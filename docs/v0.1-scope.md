## 1. Goal

An AI agent that takes a slow Java/Spring service, diagnoses the performance
bottleneck, applies a fix, and proves improvement with benchmarks — in a single
autonomous loop:

```
benchmark baseline -> capture JFR under load -> aggregate -> hypothesis
-> apply one change -> rebuild -> re-benchmark -> keep or revert -> iterate
```

v0.1 proves the loop end-to-end against one known bottleneck. Everything else
(multi-bottleneck targets, code-level fixes, model training) is later.

## 2. Decisions (locked)

- **Language/stack**: Java 21 + Spring Boot 4.1.1 + Spring AI (function calling).
- **Single agent loop** — no multi-agent split in v0.1.
- **AI proposes, pipeline disposes**: the model does reasoning and picks the
  fix; the harness enforces truth. Every change goes through
  change -> rebuild -> smoke -> benchmark -> keep/revert. No path skips the
  benchmark gate.
- **k6 profile**: the reference repo's standard — 200 VUs, 60s steady, 10s
  ramp (+5s down), 10% writes / 90% reads, entity count 50. Changing load
  changes the bottleneck; keep it fixed so results are reproducible.
- **Target**: stock spring-petclinic (form-based scenario), NOT
  petclinic-degraded (its degradation is static — README/tests; runtime code
  is byte-identical to stock petclinic, and the local clone is broken).

## 3. The v0.1 case: petclinic classloader lock

Ground truth (from `java-backend-quality-analyzer/evidence/advanced/h3/spring-petclinic/`
— the *stock-app* evidence set, not petclinic-degraded):

- At 200 VUs, petclinic collapses on a **fat-jar classloader lock**:
  71,738 `jdk.JavaMonitorEnter` events (p95 407ms, max 1490ms, CRITICAL) —
  the dominant event class. ThreadPark (p95 1000ms) and SocketRead
  (p95 105ms) are also CRITICAL — plausibly downstream of the lock, unproven.
- Measured baseline: rps ~189, p95 ~2500ms, failRate 0 (threshold
  p95<500ms → verdict FAIL). The earlier ~240 rps / ~2105ms figures were
  petclinic-degraded's; the stock app measures somewhat worse.
- Candidate fix — **hypothesis, never measured**: run the app from extracted
  classes (unpack/layer the jar in the target Dockerfile) instead of
  `java -jar` on the fat jar. No post-fix benchmark exists anywhere in the
  reference repo, so the fix's magnitude is unknown; build-order step 2
  measures it by hand before any LLM depends on it.

Why this is the right first case:

- Ground truth is known → we can score whether the agent's hypothesis was
  *correct*, not just whether a number moved.
- Fix is packaging/config-level → low reliability cost for AI-driven changes.
- Existing h3 evidence for the *stock* app (JFR text dumps +
  `diagnosis-report.md`) is the validation set for our Java JFR aggregator
  before the LLM ever sees data.

## 4. Architecture

Three modules (Maven, single repo):

```
agent-core/      Spring AI loop, tool @Beans, prompt, hypothesis/keep-revert logic
target-runner/   port of run-experiment.sh docker path: build -> compose up
                 -> smoke gate -> k6 -> JFR capture; Testcontainers for lifecycle
evidence/        load-report + experiment-trajectory schemas, writers, store
```

### 4.1 Tools (Spring AI function calling, plain Java @Beans)

| Tool | Signature (sketch) | Notes |
|---|---|---|
| `runBenchmark` | `runBenchmark() -> LoadReport` | k6 via `ProcessBuilder` or compose `run`; parse k6 summary JSON with Jackson; returns the fixed load-report shape (rps, p50/p95/p99, failRate, verdict, breached thresholds). |
| `captureAndAnalyzeJfr` | `captureAndAnalyzeJfr() -> JfrReport` | Restart target with JFR opts, run load, stop (dumponexit flush), parse with `jdk.jfr.consumer` (`RecordingFile.readAllEvents`), return **aggregated** report — never raw events. |
| `readSource` | `readSource(path) -> String` | Read-only file access inside the target working tree. |
| `applyChange` | `applyChange(description, edits) -> ChangeResult` | Applies edits (config or code) to the target working tree. Git-backed: every applied change is a commit; revert is `git reset --hard <baseline>`. |

### 4.2 Agent loop (pseudocode)

```
baseline = best-of(runBenchmark() x 3)          // record variance as noise floor
state    = git commit "baseline" in target tree
for i in 1..MAX_ITERATIONS (5):
    jfr    = captureAndAnalyzeJfr()
    action = llm.decide(history, baseline, jfr)  // hypothesis + ONE change
    applyChange(action)
    if !rebuildAndSmoke(): revert(); continue
    result = runBenchmark()
    evidence.record(hypothesis, before, change, after, delta)
    if result.beats(baseline, beyondNoise):
        baseline = result; state = commit("keep: " + action.description)
    else:
        revert to state
    if result.p95 < 500ms and no breached thresholds: break  // target met
```

- ONE change per iteration — never compound changes, or attribution is lost.
- Noise floor: baseline run 3x; an improvement must exceed observed variance.
- Max 5 iterations; stop early if k6 thresholds pass.

### 4.3 JFR aggregation (the research component, v0.1 shape)

Port of `jfr-diagnose.sh` logic to pure Java via `jdk.jfr.consumer`.
Events to consume and aggregate:

| Event | Aggregation |
|---|---|
| `jdk.ExecutionSample` | Top-15 stacks (merged, truncated frames) → hottest methods; **also keep the top-3 raw frames per top stack** — the known bottleneck lives in JDK frames (`ClassLoader.loadClass`), which a first-non-JDK-frame rule alone would truncate away |
| `jdk.JavaMonitorEnter` | Count + p50/p95/max; top contended `monitorClass` |
| `jdk.ThreadPark` | Count + p95; top parks with first non-JDK frame |
| `jdk.SocketRead`/`SocketWrite` | Count + p95 (external I/O signal) |
| `jdk.GCPhasePause` | Count + p99 (GC pressure) |
| `jdk.ObjectAllocationSample` | Count; top allocating classes |
| `jdk.JavaErrorThrow` + `jdk.ExceptionThrow` | Count; top thrown classes |

Output: a compact structured `JfrReport` (JSON, target ~2–5 KB) with counts,
percentiles, severity classification, and top-N tables. Severity thresholds
copied from `jfr-diagnose.sh` (env-overridable there → a `Thresholds` config
record here), e.g. lock p95 ≤1/5/20ms, SocketRead p95 ≤1/5/20ms,
GC p99 ≤10/50/200ms.

Validation gate before the LLM loop: run the aggregator on the existing h3
`profile.jfr` evidence and confirm it reproduces the "lock contention,
JavaMonitorEnter dominant" signal.

### 4.4 Evidence (trajectory + eval store)

Reuse the reference formats:

- `load-report.json` — fixed shape:
  `{repo, dateUtc, rps, totalRequests, latency{avg,p50,p95,p99,max},
    failRate, checkPassRate, thresholds{verdict, breached[]}}`
- Per-iteration experiment record, modeled on `evidence/experiments/TEMPLATE-*.md`:
  Hypothesis → Evidence Before (metrics + key JFR signal) → Change (one
  sentence, one change) → Evidence After (before/after/delta) → Kept/Reverted.
- Full trajectory log (tool calls + LLM responses) per run — this is the
  dataset for any later model-training phase.

## 5. Target runner specifics (inherited, already solved)

From the reference repo's docker envelope (`service/advanced/docker/`):

- Target image: `eclipse-temurin:21-jre`, resource budget 2 CPU / 2 GB,
  JVM pinned `-XX:ActiveProcessorCount=2 -Xms1536m -Xmx1536m`.
- k6 container: 1 CPU / 512 MB, official `grafana/k6` image.
- Healthcheck: TCP connect to 8080 (actuator not guaranteed on arbitrary repos).
- Smoke gate before full run: 2 VUs / 5s; require `http_reqs.count>0` and
  `checks.rate>0`, else the run is a NOT_TESTABLE finding, not a crash.
- k6 exit 99 (threshold breach) = measured FAIL, not an error.
- JFR: `-XX:StartFlightRecording=settings=profile,dumponexit=true,filename=/jfr-repo/...`
  with evidence dir bind-mounted at `/jfr-repo`; `stop_grace_period: 15s` so
  dumponexit flushes. **Never `disk=true`** — chunk writes fail on Docker
  Desktop Windows bind mounts. Use `MSYS_NO_PATHCONV=1` semantics /
  `cygpath -w` equivalents when constructing paths from Git Bash.
- k6 script: render from the reference template (form scenario for petclinic:
  `POST /owners/new` → id from redirect `Location`, `GET /owners/{id}`),
  committed as an artifact — "artifact is the contract, never regenerate".

## 6. Success criterion (v0.1 done = )

On stock spring-petclinic at the standard profile (200 VUs / 60s):

1. Agent's recorded hypothesis names **lock contention / classloading** as the
   bottleneck category (checked against known ground truth).
2. Agent converges on a working fix (jar unpack or equivalent) and achieves a
   **measured p95 improvement beyond the noise floor** (baseline p95 ~2500ms;
   headroom down to the 500ms threshold) within **≤5 iterations**.
3. Full evidence trail exists: baseline report, per-iteration experiment
   records, final load-report showing before/after.

Pass tiers — the fix's magnitude is a hypothesis until build step 2 measures
it by hand:

- **PASS (v0.1 done)**: hypothesis names the right category + measured
  improvement beyond noise + complete evidence trail.
- **STRETCH**: p95 < 500ms (k6 verdict PASS). If the unpack fix alone lands
  short because the next bottleneck emerges, that is data for the next
  iteration — not a v0.1 failure, provided the loop used its remaining
  iterations honestly.

## 7. Explicitly out of scope (v0.1)

- Multi-bottleneck or self-seeded targets (e.g. degraded `practice-mvc`
  variants) — phase 2, once the loop works.
- Free-form code refactoring by the agent (fix space is small; petclinic case
  needs only packaging/config-level changes).
- Multi-agent architectures.
- Model fine-tuning / diagnosis training (needs trajectory data from v0.1 first).
- Native-mode (non-docker) target running.
- WebFlux/reactive targets, Kafka, Redis/MySQL infra variants.

## 8. Build order (dumbest loop first)

1. `evidence` schemas + `target-runner`: port build → compose → smoke → k6 →
   report for petclinic. Verify against the stock baseline (rps ~189,
   p95 ~2500ms, verdict FAIL).
2. **Manual fix-validation gate** — no code, one benchmark: hand-edit
   `Dockerfile.target` to the unpack/layered-jar fix, run the pipeline once,
   measure the real post-fix p95. This converts the load-bearing hypothesis
   (§3) into data before the agent depends on it, and calibrates the §6 pass
   tiers. If the fix is a dud, find the real fix now, by hand, where
   iteration is cheap.
3. `captureAndAnalyzeJfr` aggregator; validate on the stock h3 `profile.jfr`.
4. `applyChange` + git-backed revert in target working tree.
5. Wire the Spring AI loop with the 4 tools; prompt with hypothesis menu seeded
   from the 7 jfr-diagnose.sh hypotheses.
6. Full run against success criterion; iterate on prompt/aggregation only where
   the evidence shows failure.

## 9. Risks & open decisions

### Failure taxonomy for the agent loop

The model will misbehave; the loop must treat failures as data, not crashes.
Tool failures are returned to the model as tool results, never thrown:

| Failure | Handling |
|---|---|
| Malformed edit / invalid tool args | Reject without applying; return the validation error to the model. One retry, then count the iteration as wasted and continue. |
| Valid edit, build fails | Revert; feed the compiler error back as the next tool result. |
| Build passes, smoke gate fails | Revert; feed smoke output back. |
| Benchmark regresses | Revert silently; record in the experiment record. |
| LLM/provider error mid-iteration (timeout, rate limit, empty reply) | Retry the LLM call with bounded backoff; if it still fails, end the run as INCOMPLETE — already-kept changes and evidence remain valid. |
| Docker daemon down / compose fails mid-run | End run as INCOMPLETE; never keep a change that was never benchmarked. |

### Benchmark comparability rule

k6 numbers are only comparable across iterations if every run starts from
identical state: the runner always recreates the stack (fresh containers, DB
reset). Petclinic's H2 resets on restart, so recreate-on-every-run is
sufficient — never benchmark against a warm, previously-loaded container.

### Model/provider (decide before build step 8)

- Axis that matters: tool-calling reliability, then context size, then cost.
- API key via env var only — never in the repo.
- Guardrails: max tokens per run; log token usage + cost per LLM call into
  the trajectory (this data feeds the phase-2 "is a fine-tuned smaller model
  worth it" question).

### Time budget expectation

One iteration ≈ JFR capture (60s load) + rebuild (1–2 min) + benchmark (60s)
+ LLM latency ≈ 4–6 min. A full 5-iteration run ≈ 25 min. A run that looks
quiet is probably not hung.

## 10. Design resolutions (from pre-build review)

1. **Module dependency graph**: `evidence` (no deps) ← `target-runner`
   (plain Java library, no Spring AI) ← `agent-core` (Spring Boot/AI).
   Tools in `agent-core` are thin adapters over `target-runner` services.
2. **`readSource` confinement**: resolve + normalize against the target root;
   reject (via error envelope) any path escaping it; don't follow symlinks
   out; 100 KB read cap.
3. **`applyChange` edit format — locked**: full-file replacement as
   `[{path, content}]`, per-file cap ~400 lines. No unified diffs (LLM diff
   output is too unreliable; v0.1's fix space is small files). Revisit only
   if phase 2 needs source-level patches on large files.
4. **Tool error envelope**: every tool returns
   `{ok: bool, data: ... | null, error: {type, message} | null}`
   (`ToolResult<T>`). The model always gets parseable JSON.
5. **Noise floor — locked**: `noiseFloor = max(5% of median baseline p95,
   max−min spread of the 3 baseline p95s)`. Keep a change iff
   `new p95 < median baseline p95 − noiseFloor` AND failRate not worse.
6. **JFR always on**: one stack mode — every benchmark run boots with JFR
   opts, runs load, gracefully stops, harvests `profile.jfr`. Overhead is
   small (~1–2%) and constant across runs, so comparability holds. Every
   benchmark therefore yields a fresh recording;
   `captureAndAnalyzeJfr` analyzes the recording of the run it belongs to
   (§10.15 — never a bare latest-file glob, so smoke recordings can't be
   mistaken for benchmarks).
7. **Packaging ownership**: target-runtime packaging (`Dockerfile.target`,
   target compose overrides) lives inside the target working tree → under
   target git → agent-editable and revertable. The generic envelope (k6
   compose service, resource limits, healthcheck) lives in the project repo
   → outside the agent's reach.
8. **Model/provider**: decision checkpoint at build step 8, not a design
   gap. Default: pin Spring AI 1.0.x GA first, use its `@Tool` idiom, pick
   provider by available API key; tool-calling reliability is the criterion.
9. **Run-ID**: `yyyyMMdd-HHmmss-<8char>` minted once per agent run by
   `AgentLoop`. Layout: `evidence/<run-id>/baseline-{1..3}/`,
   `evidence/<run-id>/iter-<n>/` (each holding `load-report.json`,
   `profile.jfr`, `experiment-record.json`), plus
   `evidence/<run-id>/trajectory.jsonl`.
10. **Windows paths in Java**: the final system never touches Git Bash —
    `ProcessBuilder` invokes docker directly, so `MSYS_NO_PATHCONV`/
    `cygpath` do not apply. One utility (`DockerPaths.toMount(Path)`):
    absolute path with backslashes → forward slashes (`C:/...`), which
    Docker Desktop accepts for bind mounts. The shell gotchas in §5 apply
    only to manual compose debugging from Git Bash.
11. **Fix-validation gate**: build-order step 2. The unpack fix is
    hand-applied and hand-measured before the agent loop exists; its
    measured p95 calibrates the §6 pass tiers. The target tree is reset to
    `baselineSha` afterwards — the agent must start from the unfixed state.
12. **`applyChange` file semantics**: a `path` that doesn't exist creates
    the file; an existing file is replaced whole. No deletions in v0.1 —
    deletion is what `revertTo()` is for.
13. **Revert vs. `.gitignore`**: `git clean -fd` spares *ignored* untracked
    files, so an agent-created file matching the target's `.gitignore`
    would survive a revert. Revert is therefore `git reset --hard` +
    `git clean -fd`, then assert `git status --porcelain` is empty — if
    not, fall back to `git clean -fdx` (also drops `target/`, forcing the
    full rebuild the next iteration does anyway).
14. **Rebuild = image rebuild, not just Maven**: `rebuildAndSmoke()` is
    `mvn package` **and** `docker compose build` → `up -d --wait` → smoke.
    The unpack fix changes the Dockerfile, which Maven alone won't pick up;
    skipping the compose build silently benchmarks the old image.
15. **Per-benchmark JFR naming**: every run gets its own subdir
    (`baseline-1..3`, `iter-<n>`, `smoke-<n>`) and boots with
    `filename=/jfr-repo/<subdir>/profile.jfr`; the host subdir is created
    *before* `up` — if it's missing, JFR fails to start and the JVM
    continues silently without a recording. Analysis targets the run's own
    subdir, never "latest file".
16. **Compose project isolation + k6 output mount**: every compose
    invocation passes `-p <run-id>` so runs can't collide with orphaned
    containers/networks from a previous run, and the k6 service
    bind-mounts the evidence dir (`K6_SUMMARY_OUT=/evidence/...`) so the
    summary JSON lands on the host.
