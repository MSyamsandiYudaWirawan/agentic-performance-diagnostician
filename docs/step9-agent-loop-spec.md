## Part 0 — Mental model (read this first)

You have never seen an agent loop. Here is the whole idea in one paragraph:

> An agent loop is a **while-loop that alternates between an LLM and your
> code**. Your code gathers evidence (benchmark numbers, profiler output,
> source files) and hands it to the LLM as text. The LLM replies with a
> structured decision. Your code *executes* that decision against the real
> world (edit files, rebuild, measure), judges the outcome with deterministic
> rules, and loops. The LLM never touches the world directly; it only
> proposes. Your loop disposes.

That last sentence is the project's locked decision §2: **AI proposes,
pipeline disposes.** Everything in step 9 is machinery around that alternation.

### The Saga mapping (you already know this pattern)

This is a Saga with the LLM as the (fallible) decision source:

| Saga concept                  | Here                                                       |
|-------------------------------|------------------------------------------------------------|
| Orchestration saga            | `AgentLoop` — one class calling steps in order             |
| Compensating transaction      | `revertTo(lastKeptSha)` — undo any unproven change         |
| Forward retry w/ backoff      | LLM infra errors: bounded retry → give up                  |
| Business rejection (no retry) | invalid decision JSON: one retry → WASTED                  |
| Idempotent resume             | reload RUNNING run, verify `HEAD == lastKeptSha`, continue |
| Process manager state         | Postgres rows (`run`, `iteration`, `trajectory_event`)     |
| Timeout on downstream call    | provider HTTP timeout (D7)                                 |
| Dead-letter                   | run status `INCOMPLETE` / `ABORTED` with evidence retained |

If you explain `AgentLoop` to a colleague, say: "it's an orchestrating Saga
whose compensation is `git reset`, and whose step logic is partly generated by
an LLM under a schema contract."

### Glossary

- **decide turn** — one LLM call: we send context, the model investigates
  (may call tools) and must finally answer with one decision JSON object.
- **keep / revert** — after measuring a change: keep advances the reference
  state (a new "last kept sha"), revert rolls the tree back to it.
- **WASTED iteration** — an iteration that burned budget without producing a
  measurable change (bad decision twice, no-op edit) . Distinct from REVERTED,
  which *was* measured and lost.
- **noise floor** — how much a metric wobbles between identical runs; only
  deltas *beyond* the floor count as improvement. Computed once per run from
  the 3 baseline runs (§10.5).
- **guardrails** — hard caps (dollars / wall-clock / tokens / iterations) that
  abort the run. A runaway loop must cost at most the cap.
- **single-flight** — at most one RUNNING run ever; two concurrent benchmarks
  share the Docker VM and destroy each other's noise floors (§10.27).
- **janitor** — on startup, tear down orphaned docker compose projects from
  killed runs so they don't eat the VM budget.
- **trajectory event** — one row per LLM request/response/tool call with token
  counts and cost; the phase-2 dataset (§4.4).

## Part 2 — Timing: what one run looks like on the clock

### Baseline phase (once, ~10 min)

For k = 1, 2, 3 — each is a full stack cycle, labels `baseline-1..3`:

```
up("baseline-k", jar) → runK6("baseline-k", full) → stopAndHarvest("baseline-k")
→ analyze(jfr, previous=null, …) → createJfrReport → down()
```

(The `BenchmarkRunner.run("baseline-k", false)` call does k6 + parse + persist
of the load report; `stopAndHarvest` + `analyze` + `createJfrReport` handle the
profiler side. Note: the loop composes these primitives directly — it does
**not** go through `JfrCapture`, whose captured row has an empty payload by
design. D6.)

Then compute (see Part 6): reference = best-of-3, noise floors per metric.
Persist on the run row (V2 columns). **The last baseline recording
(`baseline-3`'s `JfrReportDto`) becomes the first decide-turn context.**

### One iteration (~4–6 min)

```
DECIDE   context = {reference metrics, floors, last-kept JfrReport (w/ diff),
         ledger, history} → decide turn (readSource only, ≤10 calls)
         → decision JSON → validate → (invalid: 1 retry → WASTED)
APPLY    ChangeApplier.apply(dec.change) → sha Sₙ    [rejections → WASTED]
REBUILD  TargetBuilder.build                          [BuildFailedException → revert, REVERTED]
TESTS    if javaTouched: CodeTouchGate.runTests       [fail → revert, REVERTED]
SMOKE    up("smoke-n", jar) → run("smoke-n", smoke) → down()
         [verdict NOT_TESTABLE → revert, REVERTED]
MEASURE  up("iter-n", jar) → run("iter-n", full) → stopAndHarvest("iter-n")
         → analyze(jfr, previous = last-kept recording) → createJfrReport → down()
JUDGE    KeepRule(decision, reference, result, iter-n JfrReport, floors)
         keep  → lastKeptSha = Sₙ; reference = result; last-kept recording = iter-n
         revert→ ChangeApplier.revertTo(lastKeptSha)
         → createIteration row (outcome, keepType, finding) → next n
```

Read the MEASURE step carefully — it encodes two scope rules:

- **One benchmark per iteration.** The recording produced while measuring the
  change is *also* the diagnosis input for the next decide turn. There is no
  separate "diagnosis load run" — that would double the cost for nothing.
- **Diff base (§10.32):** `analyze(..., previous = the current kept state's
  most recent recording)`. After a KEPT iteration that's `iter-n`; after a
  REVERTED iteration the kept state didn't change, so it's still the previous
  kept recording (never the reverted iteration's).

Why smoke is its own stack cycle: JFR writes to the subdir fixed at container
boot (`JFR_SUBDIR`). If smoke shared `up("iter-n")`, its load would pollute the
iteration recording. §10.15: smoke artifacts live in `smoke-<n>`, never
harvestable. `up()` already creates the label's subdir, so no extra mkdir is
needed.

### Termination

- iteration cap (default 5, guardrail-configurable) reached → `COMPLETED`
- guardrail cap exceeded → cleanup + `ABORTED` (Part 8)
- infrastructure failure (docker/k6/provider dead after retries) → `INCOMPLETE`
- per-target target vectors (§6) are **step-10 territory** — step 9 terminates
  on the cap only. The global p95<500ms stays verdict annotation (§10.5).

## Part 3 — State machines (the whole logic of `AgentLoop`)

Run status (already in the DB): `RUNNING → COMPLETED | INCOMPLETE | ABORTED`.

Iteration outcome per row: `KEPT | REVERTED | WASTED | INCOMPLETE`.

```
                 ┌────────────────────────── guardrail check ───────────────┐
                 ▼                                                          │
 ┌───────┐   ┌────────┐   ┌───────┐   ┌────────┐   ┌─────────┐   ┌───────┐ │
 │DECIDE │→ │ APPLY  │→ │REBUILD│→ │ SMOKE  │→ │ MEASURE │→ │ JUDGE │─┘
 └───┬───┘   └───┬────┘   └───┬───┘   └───┬────┘   └────┬────┘   └───┬───┘
     │            │            │           │             │            │
  invalid ×2   rejection    build/test   NOT_TESTABLE  infra throw   keep → KEPT
  no-op edit                fail         fail          (k6, docker)  else → REVERTED
     │            │            │           │             │
     └────────────┴──────┬─────┴───────────┴─────────────┘
                         ▼
              WASTED or REVERTED row, next iteration
  (row outcome INCOMPLETE + run INCOMPLETE only on infra failure)
```

Numbering: iteration n = max(existing n for the run) + 1 — WASTED rows count
as used iterations; a resumed run never reuses an n whose row exists.

## Part 4 — Design decisions to ratify (D1–D7)

**D1 — The decide turn exposes `readSource` ONLY; the loop applies changes.**
The model receives the JFR report + baseline in the prompt context,
investigates via `readSource`, and answers with the decision JSON. The loop —
not the model — executes `dec.change` through `ChangeApplier`, after
`DecisionValidator` passes. Why not let the model call `applyChange`/`
runBenchmark` mid-turn (all 4 tools exist and work, step 8 proved it):

1. §10.21 is literal: invalid decisions are *"rejected before anything is
   applied"*. With model-driven apply, a decision can only be validated
   *after* the tree already changed — you'd compensate by reverting commits,
   and "exactly one change per iteration" becomes a hope instead of a fact.
2. §4.2's pseudocode is loop-side: `applyChange(dec.change)`.
3. "Must runBenchmark after every change" becomes a *guarantee* instead of a
   prompt instruction the model might skip.
4. Audit trail (tree_sha, files_touched, keep accounting) stays mechanical.

The tools remain callable (gates, manual use); step 9 just doesn't hand the
model the ones with side effects. `DiagnosticTools.setPreviousJfrReport`
stays unused this step — the loop passes the previous DTO straight to
`JfrAnalyzer`.

**D2 — One seam for everything outside the JVM: `TargetPipeline`.** The loop
must be dry-run-testable without Docker/k6/Postgres (the verify gate demands
fake-LLM mechanics tests). So `AgentLoop` talks to an interface
(`rebuild / smoke / benchmark`) with two implementations: `DockerTargetPipeline`
(real chain, mirrors the step-8 gate construction) and `FakeTargetPipeline`
(test tree). Same idea one level up: `ChatPort` wraps `ChatClient` because
faking Spring AI's builder chain is misery, and `DecideTurn` wraps the whole
LLM interaction so the gate can script it. **Seams at the unstable/external
boundaries, real logic in between** — this is the testability pattern to take
away from this step.

**D3 — Retry policy is two-track, per the failure taxonomy.**

- *Model's fault* (schema-invalid JSON after fence-stripping): one retry with
  the validation error quoted back; still bad → **WASTED**, run continues.
- *Infrastructure's fault* (HTTP timeout, 429/5xx, IO): bounded retry with
  backoff — 2 retries, 30 s then 60 s (env-tunable); still failing → run
  **INCOMPLETE** (taxonomy row 5). Build-step 9's "a timeout counts as a
  failed LLM turn" means exactly this: the timeout must surface *as a failed
  turn entering a retry path*, never as a silent clock-burn (D7).

**D4 — Ledger semantics (§10.22, advisory only).** In-memory
`Map<String,Double>` scores for H1–H7, start 0.0. The model proposes
strengthen/weaken per iteration; the loop applies a fixed step ±0.2, clamped
to [0,1] — deterministic arithmetic, model chooses direction only. Never gates
anything; persisted verbatim on each iteration row.

**D5 — Trajectory events cover pipeline actions too.** Beyond
`LLM_REQ`/`LLM_RESP` (with tokens/cost), the loop logs `TOOL_CALL`/
`TOOL_RESULT` rows for its own pipeline actions (apply, benchmark, harvest)
and for every model-initiated `readSource` (the wrapper logs them — Spring AI
doesn't expose per-tool-call observation without extra plumbing). One queryable
stream of everything that happened, tokens attached where they exist.

**D6 — Loop composes JFR primitives directly.** `JfrCapture` (the tool path)
persists a placeholder row with an empty payload, expecting the tool flow to
fill it; the loop instead does `stopAndHarvest → analyze → createJfrReport`
in one shot with the full payload — no empty-row dance, no row updates.

**D7 — Explicit provider HTTP timeout.** Add a `RestClientCustomizer` bean in
`AgentConfig` that sets connect/read timeouts (env `DIAG_LLM_TIMEOUT_MS`,
default 120000) via `ClientHttpRequestFactorySettings`. Spring AI's
auto-configured client uses the autoconfigured `RestClient.Builder`, so
customizing the builder covers it. **Verify while implementing M2** (Spring AI
2.0.1): if the starter builds its own factory, the fallback is setting the
timeout on the `ChatModel` bean's client directly. A hang with no timeout
burns the wall-clock guardrail silently — the exact failure this exists to
prevent (measured motivation: the local dev config here runs a 50-minute
provider timeout).

**D8 — Mechanism signal names match by exact key only.** (User decision,
2026-09-24, overriding the earlier exact-then-substring sketch.) The exact
keys are already in the model's input — the JFR report JSON has them as
literal keys and the system prompt lists them — so a misspelled prediction is
a model failure to surface, not rescue: fuzzy matching would corrupt the
prediction-accuracy eval dimension (§10.21) and is ambiguous anyway
(`"Socket"` substring-matches `SocketRead` and `SocketWrite`). The not-found
revert reason lists the valid keys — the model self-corrects across
iterations; a near-miss costs at most one mechanism-keep opportunity.

### 5.2 `Baseline` + `NoiseFloors` (pure records)

```java
record NoiseFloors(double p95FloorMs, double rpsFloor, double p50FloorMs) {
    static NoiseFloors fromBaselines(List<LoadReportDto> three) { …}
}

// implemented 2026-09-24 as a plain final class: (reference, floors) only —
// no `runs` field; the three source rows are persisted load_reports, the DB
// is the audit trail (user decision, accepted).
class Baseline { LoadReportDto reference; NoiseFloors floors;
    static Baseline of(List<LoadReportDto> three) { … } }
    static Baseline of(List<LoadReportDto> three) { …}
}
```

Math (§10.5, pinned so tests can pin it too):

- `reference` = best-of-3: `rps = max(rpsᵢ)`, and for latency fields `min`
  (the app's best day — the hardest baseline to beat; prevents noise-keeps).
- floor(metric) = `max(0.05 × median, max − min)` in the metric's own units,
  computed for p95, rps, and p50 (p50 is needed by the MECHANISM branch).
- Step-4 calibration data: consecutive baselines spread ≈ 2.4% → the 5% term
  dominates here; if a future gate shows spreads > 5%, that's noise-floor
  calibration work, not a loop bug.

### 5.3 `KeepRule` (pure — the heart of the step)

```java
record KeepDecision(boolean keep, String keepType /* RPS|P95|MECHANISM|null */, String reason) {
}

static KeepDecision evaluate(DecisionDto d, LoadReportDto ref, LoadReportDto result,
                             JfrReportDto resultJfr, NoiseFloors f, double p95Bound)
```

Semantics — evaluate (a) then (b), first match wins:

**(a) classic (§10.5a):** `result.rps − ref.rps > f.rpsFloor` **or**
`ref.latency.p95 − result.latency.p95 > f.p95FloorMs`, **and**
`result.failRate <= ref.failRate` → keep, type `RPS` if the RPS branch fired
(check it first — it's the primary signal per rev 5), else `P95`.

**(b) verified mechanism (§10.5b), all four required:**

1. prediction confirmed: the signal named by
   `d.prediction().mechanismSignalToEliminate()` dropped —
   `countDelta < 0 && |countDelta| / baseCount > 0.5` where baseCount comes
   from `resultJfr.diff().deltas()` + the previous kept report's count
   (pass the previous report in, or read it from the diff base — see contract
   note below). Signal-name matching: **exact key only** (D8) — no match →
   branch fails, reason lists the valid keys.
2. ≥1 metric improved beyond its floor: rps ↑, p95 ↓, **or p50 ↓** beyond
   `f`.
3. `result.failRate <= ref.failRate && result.checkPassRate >= ref.checkPassRate`.
4. tail bounded: `result.latency.p95 <= ref.latency.p95 × (1 + p95Bound)`.
   → keep, type `MECHANISM`.

Neither → revert (`keep=false`, type null, `reason` human-readable with the
numbers — it feeds the iteration row and the next decide turn).

*Contract note:* to make (b) self-contained, `evaluate` takes the previous
kept `JfrReportDto` as an extra parameter (`prevJfr`), reads base counts from
`prevJfr.signals().get(name).count()`, and uses `resultJfr.diff()` only as a
cross-check if present. That keeps the rule testable from two plain DTOs.

**Ground-truth unit tests (§10.5's own demand — write these FIRST):**

| # | fixture (canned DTOs, REF numbers)                                                                                     | expect                                                         |
|---|------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------|
| 1 | jar-unpack saddle: ref rps 189 → result 277, p95 2500 → 3100, failRate 0→0, `JavaMonitorEnter` 71193 → 0               | keep, type `RPS` (classic fires first)                         |
| 2 | resource-cache falsification: rps 189 → 191, p95 2500 → 2470 (both inside floors), signals ±noise                      | revert                                                         |
| 3 | pure saddle: rps 189 → 192 (noise), p95 2500 → 3100 (+24% ≤ 50% bound), signal 71193 → 3000, p50 improves beyond floor | keep, type `MECHANISM` — the case a p95-greedy loop gets wrong |
| 4 | mechanism NOT confirmed: signal −20%, metrics flat                                                                     | revert                                                         |
| 5 | failRate worsens 0 → 0.02, rps improves beyond floor                                                                   | revert (classic guard)                                         |
| 6 | p95 regression over bound: 2500 → 4000 (+60%), signal −96%, rps flat, p50 improves                                     | revert (bound bites)                                           |

Floors for fixtures: pick e.g. rpsFloor 9.45 (5% of 189), p95Floor 125,
p50Floor 5 — assert against those constants, don't compute them in the test.

### 5.7 `DecideTurn` (seam) + `SpringAiDecideTurn`

```java
record DecideResult(DecisionDto decision /*null on failure*/, String error,
                    boolean infraFailure, long tokensIn, long tokensOut, String rawText) {
}

interface DecideTurn {
    DecideResult decide(int n, DecideContext ctx);
}
```

`SpringAiDecideTurn` flow: build context → trajectory `LLM_REQ` → `ChatPort.chat`
→ `LLM_RESP` (tokens; cost = tokens × prices from `LoopConfig`) → fence-strip
(``` ```json … ``` ``` wrappers are common; strip leading/trailing fences, then
trim) → `DecisionValidator.validate` → ok? done : retry **once** with the error
appended to the user message → still invalid → `error`, `infraFailure=false`.
Catch infra exceptions (timeout/IO/429-5xx family) separately → bounded
backoff retries (D3) → `infraFailure=true`. Tokens accumulate across retries.

### 5.8 `TargetPipeline` (seam) + `DockerTargetPipeline`

```java
record SmokeResult(boolean pass, String detail) {
}

record BenchmarkCycle(LoadReportDto load, long loadReportId, JfrReportDto jfr, long jfrReportId) {
}

interface TargetPipeline {
    Path rebuild() throws BuildFailedException;     // TargetBuilder

    SmokeResult smoke(int n);                        // up("smoke-n") → run(label, smoke=true) → down()

    BenchmarkCycle benchmark(String label, JfrReportDto prevJfr); // up → run(label,false) → stopAndHarvest → analyze(prevJfr) → createJfrReport → down
}
```

`DockerTargetPipeline` owns the run-scoped chain — construct exactly like the
step-8 gate does (`new BenchmarkRunner(stack, evidenceService, new
DockerEnvelopeGuard(), mapper, evidenceRoot, runId, targetName)`, etc.). Every
method that throws `IllegalStateException`/IO beyond `BuildFailedException`
means *infrastructure* → run INCOMPLETE (Part 8). `benchmark` also records a
`TOOL_CALL`/`TOOL_RESULT` pair (D5).

### 5.9 `AgentLoop` — the orchestrator (the class you're writing this step FOR)

Constructor: run-scoped deps (`EvidenceService`, `ChangeApplier`, `DecideTurn`,
`TargetPipeline`, `LoopConfig`, `GenParams`, `Path targetRepo`, and the V2
run-row fields via new EvidenceService methods). Two entries:

```java
String start()          // janitor already ran; createRun → originSha=currentSha() → baseline → iterate → finish

String resume(String runId)  // §10.19, see Part 9
```

State (one object, `LoopState`, or private fields — your call, keep it boring):
`runId, lastKeptSha, Baseline baseline, Map<String,Double> ledger,
List<HistoryEntry> history, JfrReportDto lastKeptJfr, long tokensIn/out,
BigDecimal cost, Instant startWall`.

Loop body = Part 3's state machine, in order, with guardrail checks at: loop
top (wall/tokens/cost/iterations), post-decide, post-benchmark. Keep each
phase a private method (`baselinePhase()`, `decidePhase(n)`, `applyPhase(n,
dec)`, `verifyPhase(n, changeResult)`, `measurePhase(n)`, `judgePhase(...)`) —
each ≤ 40 lines, each leaves the DB consistent. The judge phase composes the
deterministic `finding` string (numbers, not prose): e.g.
`"JavaMonitorEnter 71193→0 (−100%); rps 189→277 (+46%); p95 2500→3100 (+24%); keep=MECHANISM"`.

Rule: **every exit path funnels through one `finish(...)`** — status
transition + `finally`-style cleanup (revert any applied-but-unjudged commit)
so a crash never leaves a RUNNING row or a dirty tree. The step-8 gate's
finally-block pattern, promoted into the loop itself.

## Part 6 — Keep-rule reference semantics (already in 5.2/5.3 — this is the summary card)

- Reference **advances on keep**: `baseline.reference = result` (§4.2
  `baseline = result`). Noise floors do NOT re-compute — the ×3 spread is the
  run's noise model, recomputing it per-iteration would let a good iteration
  inflate its own future floor.
- Floors are one-sided in the right direction: RPS floor gates *increases*,
  p95/p50 floors gate *decreases* (improvement direction per metric).
- `keep_type` on every KEPT row; null elsewhere.

## Part 7 — System prompt (embed verbatim in `SystemPrompts.SYSTEM`)

```
You are a JVM performance diagnostician working one iteration at a time on a
Spring Boot service under a fixed k6 load profile (200 VUs, 60 s, 10 % writes).

You receive: the baseline reference metrics with their noise floors, the JFR
signal report of the current kept state (with diff vs the previous kept
recording), your hypothesis ledger, and the history of past iterations.

Hypothesis menu (category → typical JFR evidence):
  H1 external I/O        — SocketRead/SocketWrite counts and p95 high
  H2 blocking / parking  — ThreadPark dominant, pool-wait shapes
  H3 GC                  — GCPhasePause p99 high, allocation-heavy
  H4 CPU                 — ExecutionSample concentrated on few business frames
  H5 lock contention     — JavaMonitorEnter counts/p95 high, monitorClass names
  H6 allocation          — ObjectAllocationSample dominant
  H7 exceptions          — ExceptionThrow/ErrorThrow counts high

Rules:
1. ONE change per iteration. The orchestrator applies it, rebuilds, smokes,
   and benchmarks it. You cannot skip the benchmark.
2. Investigate before proposing: readSource into the suspect call path before

3. State a falsifiable prediction: name the JFR signal your change should

5. Respond with EXACTLY ONE JSON object, no prose around it:
{"hypothesis":{"category":"H1".."H7","confidence":0.0..1.0,"rationale":"..."},

 "ledger":{"category":"H1".."H7","direction":"strengthen|weaken","reason":"..."},

```

## Part 8 — Failure taxonomy → loop behavior (the complete mapping)

| Taxonomy row (scope §9)                                             | Detection                                                                | Loop behavior                                                     | Row / run outcome  |
|---------------------------------------------------------------------|--------------------------------------------------------------------------|-------------------------------------------------------------------|--------------------|
| Malformed decision                                                  | `DecideTurn` invalid ×2                                                  | no apply ever happened                                            | WASTED, continue   |
| No-op edit / path escape / cap / unadmitted template                | `IllegalArgumentException` / `TemplateNotAdmittedException` from `apply` | tree untouched; error text into history                           | WASTED, continue   |
| Valid edit, build fails                                             | `BuildFailedException`                                                   | `revertTo(lastKeptSha)`; last ~30 lines of build.log into history | REVERTED, continue |
| Build passes, tests fail (code-touch gate)                          | `runTests` false                                                         | revert; test tail into history                                    | REVERTED, continue |
| Smoke fails                                                         | `SmokeResult.pass == false` (incl. verdict NOT_TESTABLE)                 | revert; smoke detail into history                                 | REVERTED, continue |
| Benchmark regresses                                                 | `KeepRule` → revert                                                      | revert                                                            | REVERTED, continue |
| Kept change                                                         | `KeepRule` → keep                                                        | advance lastKeptSha/reference/lastKeptJfr                         | KEPT               |
| LLM/provider error                                                  | `DecideTurn.infraFailure` after backoff                                  | stop cleanly                                                      | run INCOMPLETE     |
| Docker/compose/k6 infra (`IllegalStateException` from stack/runner) | catch at phase level                                                     | attempt revert-if-dirty, stop                                     | run INCOMPLETE     |
| Envelope assertion (tampered envelope)                              | `BenchmarkRunner` throws                                                 | stop — run is *invalid*, not FAIL                                 | run INCOMPLETE     |
| Guardrail cap                                                       | check points                                                             | revert-if-dirty, stop                                             | run ABORTED        |

"Revert-if-dirty" = if `currentSha() != lastKeptSha` → `revertTo(lastKeptSha)`
— no change survives unbenchmarked, aborts included (§10.25).

## Part 9 — Resume (§10.19)

```
resume(runId):
  run = load; require status RUNNING (ABORTED requires env DIAG_RESUME_ABORTED=true)
  require single-flight: no OTHER running row (ours is this one)
  lastKeptSha = run.lastKeptSha (or originSha if no kept iteration yet)
  if currentSha() != lastKeptSha → revertTo(lastKeptSha)     // half-finished iteration discarded
  if run.baselineP95Ms == null → redo baseline phase (died during baselining)
  else rebuild Baseline from run-row numbers + floors; lastKeptJfr = latest
       kept jfr_report payload for the run (query by run + label of last KEPT
       iteration, else baseline-3)
  continue at n = max(iteration.n) + 1
```

Kill-and-resume test (gate): start a dry run, kill after iteration 1 KEPT
(don't transition status), `resume()` → tree matches lastKeptSha, iteration 2
starts, single result set is coherent (no duplicate n, no phantom RUNNING).
