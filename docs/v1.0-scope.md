## 1. Goal

An AI agent that takes a slow Java/Spring service, diagnoses the performance
bottleneck, applies a fix, and proves improvement with benchmarks — in a single
autonomous loop:

```
benchmark baseline -> capture JFR under load -> aggregate -> hypothesis
-> apply one change -> rebuild -> re-benchmark -> keep or revert -> iterate
```

v0.1 would have proven the loop on one known bottleneck. v1.0 makes the loop
an **evaluable instrument**: multiple seeded targets with ground-truth
labels, a persistent Postgres evidence store, automatic scoring of every run,
and a regression table so that prompt/model/aggregator changes are
experiments, not vibes.

v1.0 done = the target matrix runs autonomously end-to-end and gets scored
without manual collation.

## 2. Decisions (locked)

Carried from v0.1 (all still locked): Java 21 + Spring Boot 4.1.1 + Spring
AI; single-agent loop; **AI proposes, pipeline disposes** (no path skips the
benchmark gate); k6 profile fixed at 200 VUs / 60s / 10% writes; stock
spring-petclinic is target S1; one change per iteration; noise-floor keep
rule; full-file-replacement edits; JFR always on.

New for v1.0:

- **Evidence lives in Postgres** — Spring Data JPA + Flyway, JSONB payloads.
  No file-based store is built first; the DB exists from build step 1.
- **The evidence stack lives outside the measured envelope** — own always-on
  compose project (`-p diag-evidence`), own resource cap (0.5 CPU / 512 MB).
  Never inside the per-run target project: §10.16's `-p <run-id>` + `down -v`
  per run would destroy it, and a variable DB footprint inside the Docker VM
  adds p95 noise at exactly the noise-floor scale (see §9).
- **Seeded-target matrix** — petclinic plus ≥3 deterministic degraded
  variants, each carrying ground truth {category, expected fix} (§3).
- **Structured hypothesis output** — the LLM decision is a schema-validated
  JSON object; malformed output is rejected before anything is applied.
- **Hypothesis ledger** — per-category belief carried across iterations with
  explicit strengthen/weaken updates, not a fresh amnesiac guess each round.
- **Fix templates** — parameterized known fixes the agent selects *and
  parameterizes*; template application goes through the same
  commit/rebuild/smoke/benchmark gate as manual edits. No bypass.
- **Eval harness** — every run auto-scored on accuracy / effectiveness /
  efficiency; results keyed by (prompt_hash, model, aggregator_version).
- **Guardrails** — hard caps on $ / wall-clock / tokens per run → status
  `ABORTED` with partial evidence retained.
- **Gated experiments** (only after the harness can score them): RAG memory
  over past runs, self-critique pass, multi-agent A/B. Not v1.0 architecture.

Rules:

- Each seed = a committed patch applied to a pristine base clone → its own
  `baselineSha`. Deterministic; never hand-degrade a tree.
- Baseline (×3, noise floor) measured once per (target sha, k6 script sha,
  profile) and cached — re-baselining is not repeated per session (§10.24).
- S1's fix magnitude is still a hypothesis until the manual fix-validation
  gate (build step 4b) measures it; its measured p95 calibrates the §6 tiers.
- **Every** seed's expected fix is hand-validated once (apply by hand, one
  benchmark, revert) before the matrix runs — otherwise "effectiveness"
  conflates diagnosis quality with fix potency, and fix-template
  sufficiency is unproven (build step 10, §10.29).
- **S1 is a measured saddle** (REF `jar-unpack-exp`, 2026-09-03): the
  correct first fix regresses p95 while eliminating the named lock —
  `UrlJarFiles$Cache` 71,193 → 0 events, lock rate −81%, RPS +47%,
  p50 −87%, **but p95 +24%, p99 +66%, max +139%**. A p95-only greedy
  keep/revert rule would revert the right fix and oscillate on a local
  minimum for all 5 iterations — hence keep-rule v2 (§10.5). S1 ground
  truth is a *sequence of ≥3 measured/planned steps*: (1) unpack — keep
  via confirmed mechanism; (2) `spring.web.resources.cache.period` —
  **FALSIFIED** (REF `resource-cache-exp`, 2026-09-03: all deltas
  noise-level; `CachingResourceResolver` caches resolved path strings, not
  the `isReadable()` probe, and the property controls only the client-side
  `Cache-Control` header) — revert; (3) eliminate the call site —
  **candidate unverified, and "disable content-version strategy" is
  suspect**: content versioning is OFF by default in Boot, so disabling it
  is likely a no-op (same error class as step 2 — a knob nobody confirmed
  is in the circuit). The actual call site is `ResourceUrlEncodingFilter`
  → `ResourceUrlProvider` probing the classpath per rendered URL;
  neutralizing the filter needs a small config-code change, not a
  property. Pin the mechanism by reading petclinic's resource-handler
  config BEFORE spending a benchmark (open-questions A1c).
  The aggregator's validation set is three recordings: h3 (fat-jar lock
  dominant), jar-unpack-exp (shifted `JarFile`/`URLClassPath` locks),
  resource-cache-exp (same shifted locks, flat — the falsification
  reference: totals must read as "no change", not improvement).
- REF `evidence/advanced/h3/spring-petclinic/` (stock-app set) remains the
  validation set for the JFR aggregator before any LLM sees data.

## 4. Architecture

Four modules (Maven, single repo):

```
evidence/        schemas + Postgres store (Flyway/JPA) + artifact store +
                 run state machine
target-runner/   build -> compose -> smoke -> k6 -> JFR harvest; seeding
agent-core/      Spring AI loop, tools, prompt, ledger, keep/revert, guardrails
eval/            matrix runner, scoring, regression table, HTML report
```

Dependency graph: `evidence` ← `target-runner` ← `agent-core`; `eval` →
agent-core + evidence. Note the v1.0 change: `evidence` is no longer a
dependency-free plain library — it owns the Flyway schema and Spring Data
repositories (resolution §10.1 updated).

**Runtime fence ≠ module split.** All four modules run on the controller
side (our JVM + the always-on `diag-evidence` Postgres). The only things
inside the measured envelope (per-run compose `-p <run-id>`) are the target
container and the k6 container — k6 belongs there; it is the load
generator, resource-pinned so it is a constant. `eval` sits at the top of
the dependency DAG: it depends on everything, nothing depends on it, and it
judges agent-core — which is why it is a separate module, not a package
inside the loop it scores. Softest boundary of the four; if it ever merges,
the rules that must survive: eval reads the DB (never loop internals), and
the evidence contract stays stable underneath both.



### 4.1 Tools (Spring AI function calling, plain Java @Beans)

| Tool | Signature (sketch) | Notes |
|---|---|---|
| `runBenchmark` | `runBenchmark() -> LoadReport` | k6 via `ProcessBuilder`/compose; parse summary JSON; fixed load-report shape; persisted with label (`baseline-n` / `iter-n` / `smoke-n`). |
| `captureAndAnalyzeJfr` | `captureAndAnalyzeJfr() -> JfrReport+Diff` | Analyzes the recording belonging to the current run/iteration (§10.15); includes a **diff vs the run's previous recording** (per-signal count/percentile deltas, ~0.5 KB) — tells the model *why* a kept fix worked. |
| `readSource` | `readSource(path) -> String` | Read-only, confined to target root, 100 KB cap. |
| `applyChange` | `applyChange(description, edits \| fixTemplate{id,params}) -> ChangeResult` | Full-file replacement `[{path, content}]`, per-file cap ~400 lines; **or** a fix-template reference expanded server-side. Both paths commit → rebuild → smoke → benchmark. No bypass. |

### 4.2 Agent loop (pseudocode)

```
run       = db.createRun(target, promptHash, model, ...)      // status RUNNING
baseline  = cached or best-of(runBenchmark() x 3)             // noise floor
state     = target.baselineSha
ledger    = {H1..H7: neutral}
while i <= MAX_ITERATIONS (5) and not guardrails.exceeded():
    jfr    = captureAndAnalyzeJfr()                           // report + diff
    dec    = llm.decide(history, baseline, jfr, ledger)       // SCHEMA-VALIDATED
    ledger = dec.ledgerUpdate
    applyChange(dec.change)
    if !rebuildAndSmoke(): revert(); continue                 // WASTED/REVERTED
    result = runBenchmark()
    evidence.record(dec, before, change, after, delta)
    keep = verifyPrediction(dec, result, jfr)  // keep-rule v2, §10.5
    if keep:
        baseline = result; state = commit("keep: " + dec.description)
    else: revert to state
    if result.p95 < 500ms and no breached thresholds: break
run.finish(COMPLETED | INCOMPLETE | ABORTED)
```

- ONE change per iteration; malformed decision → one retry, then the
  iteration counts as WASTED and the loop continues.
- Resume: a killed run is reloadable (§10.19).

### 4.3 JFR aggregation

Unchanged from v0.1 §4.3 — the event table, severity thresholds (ported from
`jfr-diagnose.sh`, env-overridable `Thresholds` record), top-3 raw frames per

Validation gate before the LLM loop: aggregator on the REF h3 `profile.jfr`

### 4.4 Evidence store (Postgres)

Schema sketch (Flyway-owned; `payload` columns hold the same JSON the v0.1
file store would have written — `LoadReport`/`JfrReport` records remain the
Jackson contracts):

```
run(id, target_id, status[RUNNING|COMPLETED|INCOMPLETE|ABORTED],
    started_at, finished_at, provider, model, prompt_hash, aggregator_version,
    gen_params jsonb, tokens_in, tokens_out, cost_usd,
    baseline_p95_ms, noise_floor_ms)
target(id, name, base_repo, seed_patch, baseline_sha,
       ground_truth_category, ground_truth_fix, profile_hash)
iteration(id, run_id, n, hypothesis jsonb, ledger jsonb, change jsonb,
          outcome[KEPT|REVERTED|WASTED|INCOMPLETE], tree_sha,
          load_report_id, jfr_report_id, created_at)
load_report(id, run_id, label, payload jsonb, k6_summary_path)
jfr_report(id, run_id, label, payload jsonb, jfr_path, jfr_sha256)
trajectory_event(id, run_id, ts, kind[LLM_REQ|LLM_RESP|TOOL_CALL|TOOL_RESULT],
                 payload jsonb, tokens_in, tokens_out, cost_usd)
```

- Binary/raw artifacts (`.jfr`, k6 summary JSON, build logs) stay on disk
  under `evidence/artifacts/<run-id>/...`; the DB stores paths + sha256,
  never blobs.
- Every LLM call logs a `trajectory_event` with token counts and cost —
  this is the phase-2 (fine-tuning worth it?) dataset, queryable from day
  one.
- Comparability queries the file store could never answer: "iterations where
  hypothesis = H5 and fix kept, across targets", joined against
  model/prompt_hash for the regression table.

  Desktop bind mounts.
- k6 script is a committed artifact — never regenerated at runtime.
- Every compose invocation `-p <run-id>`; k6 bind-mounts the evidence dir so
  `K6_SUMMARY_OUT` lands on the host.

Additions:

- **Evidence envelope**: `docker/evidence/docker-compose.yml` — Postgres
  (own project name `diag-evidence`, own volume, capped 0.5 CPU / 512 MB),
  port 5432. Booted once by an `EvidenceStack` bootstrap (compose up +
  health poll), health-checked before each run, **never** torn down per
  benchmark. The per-run `-p <run-id>` project never references it.
- **Seeding**: `SeededTarget` applies a committed patch to a pristine base
  clone, commits, records `baselineSha` + ground-truth row. Reset between
  runs is the same `revertTo()` machinery as the loop uses.

## 6. Success criterion (v1.0 done = )

1. **Matrix autonomy**: ≥4 targets (S1–S4) each run the full loop (≤5
   iterations, guardrails active), evidence complete in Postgres, artifacts
   hashed on disk.
2. **Automated scoring**: diagnosis accuracy (final-kept hypothesis category
   vs. ground truth) ≥ 70% across the matrix; ≥2 of 4 targets reach measured
   p95 improvement beyond their noise floor within budget. Thresholds are
   defaults, env-overridable — calibrate after the first matrix run rather
   than gaming them. The headline accuracy comes from **≥2 matrix repeats**
   (LLM nondeterminism; four targets once is an anecdote); per-target detail
   is the unit of record. Metric honesty: with a fix library present,
   accuracy measures *diagnose correctly + pick/parameterize the right fix*;
   a right diagnosis with a wrong template choice is the interesting
   failure, and it stays visible in the detail.
3. **Reporting with no manual collation**: regression table + per-run HTML
   report generated straight from the DB.
4. **Guardrails + resume proven**: a capped run aborts with partial evidence
   intact; a killed run resumes from its last kept iteration.

Pass tiers: **PASS (v1.0 done)** = 1–4. **STRETCH** = accuracy ≥85% and S5
in the matrix.

S1 specifics (calibrated by the measured saddle): PASS on S1 = the agent
keeps the unpack change via the verified-mechanism path (a plain p95 rule
reverts it), then lands a follow-up that improves the final state (RPS or
p95, §10.5a) beyond noise within the ≤5-iteration budget. **STRETCH is a
per-target target vector set from fix-validation data, not the global
500ms**: e.g., S1's vector gets pinned after the iteration-3 measurement
(something like {RPS ≥ 2× baseline, p95 < baseline − 50%}); the global
`p(95)<500` k6 threshold is verdict annotation only — Little's Law says it
implies ~670 RPS on 2 CPUs, beyond this envelope's physics (§10.5).

## 9. Risks & open decisions

### Failure taxonomy (carried; unchanged)

| Failure | Handling |
|---|---|
| Malformed edit / invalid tool args / invalid decision schema | Reject without applying; return the validation error to the model. One retry, then the iteration counts as WASTED and the loop continues. |
| Valid edit, build fails | Revert; feed the compiler error back as the next tool result. |
| Build passes, smoke gate fails | Revert; feed smoke output back. |
| Benchmark regresses | Revert — *unless* the verified-mechanism keep applies (§10.5b): prediction confirmed + bounded tail regression. Recorded either way. |
| LLM/provider error mid-iteration | Bounded-backoff retry; still failing → run INCOMPLETE; kept changes and evidence remain valid. |
| Docker daemon down / compose fails mid-run | Run INCOMPLETE; never keep an unbenchmarked change. |
| Guardrail cap hit ($ / wall-clock / tokens) | Run ABORTED; partial evidence retained; resume requires an explicit flag (§10.25). |

### Benchmark comparability rule (carried + extended)

Every benchmark starts from identical state: stack recreated per run, fresh
containers, DB reset (H2 resets on restart). **New**: the evidence Postgres
must be a *bounded and constant* neighbor (own project, capped), because a
variable DB footprint inside the Docker VM shifts effective CPU/memory/disk
available to the target between runs — noise manufactured at exactly the
noise-floor scale. If capped-in-VM still shows noise, host-install Postgres.

### Specification gaming (new, v1.0)

The agent edits the target tree, and the target tree contains legitimate
performance knobs — so the loop can manufacture "improvements" that are
actually behavior changes or measurement shifts. Countermeasures are all
pipeline-side (none trust the model):

- **Read-back checks in the k6 script**: every write (`POST /owners/new`)
  is immediately followed by a GET of the new id with a content assertion —
  "fast because writes stopped landing" fails the gate, not the benchmark.
- **Envelope assertion after every run**: `docker inspect` the target
  container and assert NanoCpus/Memory equal the budget — catches any edit
  that moved the resource caps, whatever file path it took.
- **Change transparency**: every iteration records files touched + line
  counts; eval flags iterations touching anything outside
  {`src/`, `Dockerfile.target`, `application*.properties`, compose
  overrides}.
- k6 scripts and resource limits already live outside the target tree
  (§10.7) — the agent cannot edit its own ruler.

### Concurrency & host hygiene (new, v1.0)

- **Single-flight**: one active run at a time, enforced by the RUNNING row —
  a second run refuses to start while one exists. Two concurrent benchmarks
  share the Docker VM and destroy each other's noise floors.
- **Startup janitor**: before any run, find compose projects matching the
  run-id pattern that belong to no active run and tear them down; verify no
  stray containers are eating the VM budget.
- **Guardrail abort cleans up**: an ABORTED run whose tree drifted past its
  last kept sha is reverted to it — no change survives unbenchmarked.
- **Baseline cache is time-bounded** (§10.29): cross-day machine drift
  (thermals, Windows updates, VM load) can invalidate a cached baseline; a
  stale hit re-validates with one confirmation run before use.

### Model/provider (decide before build step 8)

Axis: tool-calling reliability, then context size, then cost. Key via env
var only. Provider/model id recorded per run (attribution, §10.20).

### Time & cost budget

One iteration ≈ JFR (60s load) + rebuild (1–2 min) + benchmark (60s) + LLM
latency ≈ 4–6 min; a 5-iteration run ≈ 25 min. Full matrix (4 targets +
cached baselines) ≈ ~2 h wall clock. Guardrail defaults: ~$5, 60 min, 5
iterations, token cap per run — env-overridable.

## 10. Design resolutions

Carried from v0.1 rev 2 (1–16, compressed) + new (17–26):

1. Module graph: `evidence` ← `target-runner` ← `agent-core`; `eval` over
   all. Tools in agent-core are thin adapters over target-runner services.
   **v1.0 change**: `evidence` owns Flyway + Spring Data JPA (no longer
   dependency-free).
2. `readSource` confinement: resolve + normalize against target root; reject
   escapes; no symlinks out; 100 KB cap.
3. Edit format locked: full-file replacement `[{path, content}]`, ~400
   line/file cap; no unified diffs. Fix templates are the escape valve for
   bigger changes, not diffs.
4. Tool error envelope: every tool returns `{ok, data, error}` — the model
   always gets parseable JSON.
5. Noise floors locked, per metric: `max(5% of median baseline value,
   baseline spread)` — computed separately for p95 AND RPS. **Keep-rule v2
   (rev 5)**: keep iff EITHER (a) classic — **RPS improves beyond its
   noise floor OR p95 improves beyond its noise floor**, AND failRate not
   worse; OR (b) **verified-mechanism keep** — the decision's prediction
   is confirmed (the predicted dominant JFR signal drops >50% beyond noise
   AND ≥1 latency/throughput metric improves beyond noise) AND
   failRate/checks not worse AND p95 regression ≤ bound (default 50%,
   env-tunable; calibrate — open-questions C16). Rationale (measured):
   under fixed-VU closed load, RPS ⇔ mean latency by Little's Law
   (200 = RPS × mean: 189→1058ms, 277→722ms, 303→659ms — verified), and
   RPS carries the better signal-to-noise (+47%/+9% clean moves vs. p95 in
   noise); p95 stays as the *diagnostic* signal — the S1 saddle was
   visible only as RPS-up/p95-down divergence, which an RPS-only loop
   would have celebrated and moved on. Every keep records `keep_type`
   (`RPS` | `P95` | `MECHANISM`). Termination: per-target **target
   vector** (§6) or iteration cap — the global `p95<500ms` k6 threshold
   stays as verdict annotation only: at 200 VUs on 2 CPUs it implies
   ~670 RPS ⇒ ~3ms CPU/request, which is beyond the envelope's physics
   for server-rendered Thymeleaf+JPA. Both branches have measured ground
   truth (REF): jar-unpack-exp = KEEP (mechanism confirmed, tail regressed
   +24%); resource-cache-exp = REVERT (mechanism not confirmed, metrics
   flat). Those two recordings are `verifyPrediction()`'s regression
   tests.
6. JFR always on: one stack mode; every benchmark yields its own recording;
   analysis targets the run's own subdir, never a glob.
7. Packaging ownership: target-runtime packaging lives in the target tree
   (agent-editable, revertable); the generic envelope (k6 service, limits,
   healthcheck) lives in the project repo, outside the agent's reach.
8. Model/provider: decision checkpoint at build step 8; Spring AI GA `@Tool`
   idiom; tool-calling reliability is the criterion.
9. Run-ID `yyyyMMdd-HHmmss-<8char>`; artifacts under
   `evidence/artifacts/<run-id>/`; metadata in Postgres.
10. Windows paths: final system never touches Git Bash; `DockerPaths.toMount`
    (backslashes → `C:/...` forward slashes). `MSYS_NO_PATHCONV`/`cygpath`
    only for manual Git Bash debugging.
11. Fix-validation gate: hand-apply + hand-measure the unpack fix before the
    agent exists; measured p95 calibrates §6; target reset to `baselineSha`
    afterwards; validated Dockerfile archived under `benchmarks/`.
12. `applyChange` file semantics: missing path creates; existing replaced
    whole; no deletions (that's `revertTo()`'s job).
13. Revert = `git reset --hard` + `git clean -fd`; assert clean
    `git status --porcelain`, else fall back to `git clean -fdx`.
14. Rebuild = `mvn package` **and** `docker compose build` → `up -d --wait`
    → smoke. Never benchmark a stale image.
15. Per-benchmark JFR naming: per-run subdirs (`baseline-1..3`, `iter-<n>`,
    `smoke-<n>`), host subdir created before `up`.
16. Compose isolation: `-p <run-id>` per run; k6 bind-mounts the evidence
    dir. **Never include the evidence Postgres in this project** (§5).
17. Evidence DB: Flyway migrations live in `evidence`; JSONB payloads are
    the same JSON the tools return — one contract, persisted verbatim.
18. Artifacts on disk, hashes in DB (`sha256`); DB stores no blobs.
19. Run state machine + resume: `RUNNING → COMPLETED | INCOMPLETE |
    ABORTED`. Resume = reload the RUNNING run, verify target `HEAD ==
    last kept tree_sha` (else `revertTo` it), continue at the next
    iteration. ABORTED needs an explicit resume flag.
20. Attribution: every run records `prompt_hash`, provider/model,
    `aggregator_version` — these are the regression-table keys.
21. Structured decision schema: hypothesis {category H1–H7 enum, confidence,
    rationale}, **prediction {metric to improve + direction, mechanismSignal
    to eliminate}** — the falsifiable claim keep-rule v2b verifies —,
    ledger update {category, strengthen|weaken, reason}, change {kind:
    edits | template, ...}. Invalid → rejected pre-apply (taxonomy row 1).
    Prediction accuracy is a scored eval dimension (§6.2).
22. Ledger semantics: per-category score, LLM-proposed updates recorded per
    iteration; advisory only in v1.0 — it never gates an apply.
23. Fix templates: id + params validated server-side; expansion writes into
