# v0.1 Build Steps

Status: SUPERSEDED by `v1.0-build-steps.md` (2026-09-03) — kept as reference.

Companion to `v0.1-scope.md`. Each step has a **goal**, **what to build**,
**key APIs/pointers**, and a **verify** gate — do not move on until the gate
passes. Order is deliberate: no LLM until step 8, so every piece is
deterministically testable first.

Reference repo (read-only): `C:/study/java-backend-quality-analyzer/`
(referred to below as `REF`).

---

## Step 0 — Repo & target setup

**Goal**: buildable skeleton + a working copy of the target app.

- Create Maven multi-module project: parent pom + `evidence`, `target-runner`,
  `agent-core`. Java 21, Spring Boot 4.1.1, Spring AI (add BOM now, use later).
- Environment check: Docker Desktop on the **WSL2 backend** (modern Docker
  Desktop is WSL2-only, but confirm with `docker info` — the REF envelope and
  the §10.10 `C:/...` mount form were built against WSL2). Make sure the
  Docker VM has headroom for the stack budget (service 2 CPU/2GB + k6 1
  CPU/512MB, plus Docker overhead — ≥4 CPUs / 6GB allocated).
- Clone stock spring-petclinic into `targets/petclinic` (gitignored — same
  convention as REF). The clone already has git history — no `git init`
  needed. Add the target-runtime packaging files (`Dockerfile.target`,
  compose overrides, per scope §10.7), then **make a baseline commit** and
  record its sha as `baselineSha`. This is the commit `revertTo()` resets
  to; if the packaging files aren't committed, `git clean -fd` on revert
  will delete them.
- Decide your local paths: `targets/`, `evidence/`, `benchmarks/` at repo root.
- Repo hygiene: `.gitignore` (`targets/`, `*.jfr`, `evidence/**/k6-*.json`,
  `.idea/`); root `README.md` (two paragraphs: what this is, pointer to
  `docs/`). Add `AGENTS.md` later once the layout settles.

**Verify**: `mvn -q package` green; `mvn -f targets/petclinic package -DskipTests`
produces a boot jar under `target/`; `git -C targets/petclinic rev-parse HEAD`
returns your baseline commit (i.e. there IS something to reset to);
`docker info` shows WSL2 backend.

## Step 1 — Evidence schemas

**Goal**: the data contracts everything else produces/consumes.

- Java records (Jackson) for `LoadReport`, mirroring REF `benchmarks/k6-report.js`
  output: `{repo, dateUtc, rps, totalRequests, latency{avg,p50,p95,p99,max},
  failRate, checkPassRate, thresholds{verdict, breached[]}}`.
- `ExperimentRecord`: hypothesis, evidenceBefore, change (one sentence),
  evidenceAfter, delta, kept|reverted — modeled on REF
  `evidence/experiments/TEMPLATE-*.md`.
- A small `EvidenceStore` that writes these to `evidence/<run-id>/` as JSON.

**Verify**: unit test — serialize/deserialize round-trip; parse REF's real
`evidence/advanced/h2/petclinic-degraded/load-report.json` into your `LoadReport`.

## Step 2 — k6 script for petclinic (artifact, not code)

**Goal**: a committed load-test.js you never regenerate at runtime.

- Port REF `service/advanced/k6/template-form.js` by hand for petclinic:

`evidence/advanced/h2/petclinic-degraded/load-test.js` — same shape, same slots.

## Step 3 — Target runner: build + docker lifecycle

**Goal**: Java service that builds the target and brings the stack up/down.

- `TargetBuilder`: `ProcessBuilder` of `cmd /c mvn -B -q -DskipTests package`
  in the target dir; capture `build.log`; 15-min timeout; pick boot jar
  (largest jar under `target/`, excluding sources/javadoc/.original).
  Windows: Java 21+ refuses to spawn `.cmd`/`.bat` wrappers directly, so
  plain `ProcessBuilder("mvn", ...)` fails — go through `cmd /c`.
  `docker.exe`/`git.exe` are real executables and spawn fine as-is.
- `TargetStack`: own the docker lifecycle. Easiest honest port: generate/reuse
  the REF `service/advanced/docker/` compose files (`Dockerfile.target`,
  `h2-target.yml`) and drive `docker compose` via `ProcessBuilder`
  (build → `up -d --wait` → `stop`/`down -v`). Testcontainers is fine for the
  plain container, but compose gets you the k6 container + resource limits
  for free — pick compose.
- Every compose invocation passes `-p <run-id>` (scope §10.16) — no
  container/network collisions with a previous run's leftovers. The k6
  service bind-mounts the evidence dir so `K6_SUMMARY_OUT` lands on the host.
- Resource budget baked in: service 2 CPU/2GB, JVM opts
  `-XX:ActiveProcessorCount=2 -Xms1536m -Xmx1536m`; healthcheck = TCP on 8080.

**Windows notes**:
- The final system drives docker via Java `ProcessBuilder` — no Git Bash, so
  no path mangling. Add a `DockerPaths.toMount(Path)` utility: absolute path,
  backslashes → forward slashes (`C:/...`) for bind mounts (scope §10.10).
- `MSYS_NO_PATHCONV=1` / `cygpath -w` only matter when *you* run compose
  manually from Git Bash for debugging (copy the answers from REF).
- Never JFR `disk=true` on Docker Desktop bind mounts.

**Verify**: from a JUnit/`main` run — build petclinic, bring stack up, health
poll passes, `curl localhost:8080/owners/find` returns 200, stack tears down
cleanly.

## Step 4 — Target runner: k6 execution + report

**Goal**: `runBenchmark()` works with zero AI involved.

- `BenchmarkRunner`: smoke gate first (override env: `K6_VUS=2 K6_DURATION=5s
  K6_RAMP=1s K6_ENTITY_COUNT=3`); require `http_reqs.count>0 && checks.rate>0`,
  else produce a NOT_TESTABLE `LoadReport` (a finding, not an exception).
  Smoke writes its summary + JFR into its own `smoke-<n>` subdir — never
  harvestable as a benchmark recording (scope §10.15).
- Full run with the committed profile. k6 exit 99 (threshold breach) =
  measured FAIL — parse the report anyway.
- Parse k6 summary JSON → your `LoadReport` (step 1) → write via `EvidenceStore`.

**Verify**: run against petclinic → you reproduce the *stock* baseline
ballpark (REF `evidence/advanced/h3/spring-petclinic/`): rps ~189,
p95 ~2500ms, verdict FAIL with `p(95)<500` breached. If you're wildly off,
fix the envelope (CPU/memory limits) before proceeding.

## Step 4b — Manual fix-validation gate (no code)

**Goal**: measure the unpack fix's real effect before any LLM depends on it.

The "known fix" (scope §3) is a hypothesis — no post-fix benchmark exists in
REF. Do this by hand, once, using the pipeline you just built:

- Edit `targets/petclinic/Dockerfile.target` to run from extracted classes:
  a first stage runs the fat jar with `-Djarmode=tools` (Boot 3.3+; older
  3.x: `-Djarmode=layertools`) to `extract`, the runtime stage
  `java -jar`s the unpacked app — never the fat jar.
- Run the full pipeline once (build → up → smoke → k6 @ 200 VUs → JFR).
- Record `evidence/fix-validation/load-report.json` + an experiment record;
  compare against the step-4 baseline.

**Verify** — decide, don't hope; the measured p95 picks the §6 tier:

- Big drop (≥2x, p95 ≤ ~1200ms) → the fix is real; proceed to step 5.
- Improves but stays >500ms → the lock was only part of the story; STRETCH
  tier is unlikely in ≤5 iterations. v0.1 still passes on the PASS tier —
  set expectations now.
- Doesn't move → wrong fix. Diagnose by hand now, while iteration is cheap
  and there's no LLM in the loop; update scope §3 with what actually works.

Afterwards reset the target tree to `baselineSha` (the agent must start
unfixed) and archive the validated Dockerfile under `benchmarks/` as the
reference fix (scope §10.11).

## Step 5 — JFR capture (always on)

**Goal**: every benchmark run produces a `profile.jfr`, from Java.

- JFR opts are part of the single stack mode (scope §10.6) — the target
  container always boots with:
  `-XX:StartFlightRecording=name=run,settings=profile,dumponexit=true,filename=/jfr-repo/<per-run-subdir>/profile.jfr`
  (subdir = `baseline-1..3` / `iter-<n>` / `smoke-<n>`, scope §10.15) with
  the evidence dir bind-mounted at `/jfr-repo`. Create the subdir on the
  host *before* `up` — if it's missing, JFR fails to start and the JVM
  continues silently without a recording.
- Sequence: up → run benchmark load → graceful `compose stop`
  (15s grace so dumponexit flushes) → file appears on host.
- `JfrCapture` returns the path to the recording. There is no JFR-less mode;
  `captureAndAnalyzeJfr` (step 6) analyzes the latest harvested recording.

**Verify**: `jfr summary` (JDK CLI) on the produced file shows ~60s of
profile-settings events incl. `jdk.ExecutionSample`, `jdk.JavaMonitorEnter`.

## Step 6 — JFR aggregation (pure Java, no LLM)

**Goal**: `captureAndAnalyzeJfr()` minus the LLM — the aggregated report.

- `Thresholds` config record: port the severity cutoffs from REF
  `jfr-diagnose.sh` (lock p95 ≤1/5/20ms, SocketRead p95 ≤1/5/20ms,
  GC p99 ≤10/50/200ms, park p95 ≤1/10/50ms, counts 500/5000/20000/100).
- `JfrAnalyzer`: `RecordingFile.readAllEvents(path)`; per event type build:
  - `jdk.ExecutionSample` → top-15 methods by sample count (walk
    `stackTrace.frames`, first non-JDK frame = "business frame"), **plus**
    the top-3 raw frames per top stack — the known bottleneck concentrates
    inside JDK frames (`ClassLoader.loadClass`, monitor enter), which the
    business-frame rule alone truncates away (scope §4.3).
  - `jdk.JavaMonitorEnter` → count, p50/p95/max of `duration`, top
    `monitorClass` values.
  - `jdk.ThreadPark` → count, p95, top parks w/ business frame.
  - `jdk.SocketRead`/`SocketWrite` → count, p95.
  - `jdk.GCPhasePause` → count, p99.
  - `jdk.ObjectAllocationSample` → count, top `objectClass`.
  - `jdk.JavaErrorThrow`/`jdk.ExceptionThrow` → count, top classes.
- Emit `JfrReport` JSON (~2–5 KB): per-signal {count, percentiles, severity,
  top-N table}. This — not raw events — is what the LLM will see.

**Verify** (the important gate): run the analyzer on REF's
`evidence/advanced/h3/spring-petclinic/profile.jfr`. Your report must
independently surface the known signal: `JavaMonitorEnter` dominant
(~72k events), lock contention CRITICAL — matching REF's
`jfr/diagnosis-report.md`. Also run it on your own step-5 recording.

## Step 7 — applyChange + git-backed revert

**Goal**: safe, machine-checkable mutations of the target tree.

- `ChangeApplier` in the target working tree: apply edits as **full-file
  replacement** — `[{path, content}]`, per-file cap ~400 lines (locked in
  scope §10.3; no unified diffs) — then
  `git add -A && git commit -m "<description>"`.
- `revertTo(commit)` = `git reset --hard <sha>` + `git clean -fd`, then
  assert `git status --porcelain` is empty. `clean -fd` spares *ignored*
  untracked files, so an agent-created file matching the target's
  `.gitignore` would survive — if the assert fails, fall back to
  `git clean -fdx` (drops `target/` too; the next iteration's rebuild
  recreates it) (scope §10.13).
- Track `baselineSha` at loop start; every kept change advances it.

**Verify**: unit test — apply a change (e.g. edit a properties file), commit,
revert, assert file contents and `git log` match expectations.

## Step 8 — Spring AI tool wiring

**Goal**: the 4 tools callable by the model.

- Spring AI: pin 1.0.x GA first, then use its `@Tool` idiom on `ChatClient`
  (scope §10.8). Provider = whichever API key you have; tool-calling
  reliability is the selection criterion. Register the 4 tools:
  - `runBenchmark() -> LoadReport` (step 4)
  - `captureAndAnalyzeJfr() -> JfrReport` (steps 5+6)
  - `readSource(path) -> String` (read-only, confined to target tree)
  - `applyChange(description, edits) -> ChangeResult` (step 7)
- Keep tool return types compact JSON — the model reads them verbatim.

**Verify**: a manual chat turn (test or REPL-style main) where you ask the
model to call `runBenchmark` and it does, returning real numbers.

## Step 9 — The agent loop

**Goal**: close the loop per scope doc §4.2.

- `AgentLoop` orchestrates: baseline ×3 (noise floor) → iterate ≤5:
  JFR → LLM decide (hypothesis + ONE change) → apply → rebuild+smoke →
  benchmark → keep/revert → record `ExperimentRecord`.
- System prompt: role (JVM performance diagnostician), the tool docs, the
  hypothesis menu (H1 external I/O, H2 blocking/park, H3 GC, H4 CPU,
  H5 lock contention, H6 allocation, H7 exceptions — from REF jfr-diagnose.sh),
  and the rules: one change per iteration, must call runBenchmark after every
  change, state hypothesis before acting.
- Improvement check: `result.p95 < baseline.p95 - noiseFloor` (noiseFloor from
  the 3 baseline runs' variance).

**Verify**: dry-run with a scripted fake LLM (returns a canned change) — loop
mechanics, keep/revert, and evidence records all work before real model calls
cost money.

---

## Step 10 — Full run against the success criterion

**Goal**: v0.1 done.

- Point the real loop at petclinic @ 200 VUs.
- Pass (scope §6 tier 1) = agent names lock contention/classloading,
  converges on the jar-unpack fix (or equivalent), p95 improves beyond noise
  in ≤5 iterations, evidence trail complete. Stretch (tier 2) = p95 <500ms —
  realistic only if step 4b showed the fix gets most of the way alone.
  Judge against the 4b numbers, not hope.
- If it fails, debug in this order: JfrReport quality → prompt → tool results
  → model. Change one thing, re-run, record what happened (eat your own
  evidence format).
