 # v1.0 Build Steps

Companion to `v1.0-scope.md`. Each step has a **goal**, **what to build**,
**key APIs/pointers**, and a **verify** gate — do not move on until the gate
passes. Order is deliberate: no LLM until step 8, so every piece is
deterministically testable first. Postgres comes first (step 1) because it
is cheap for us and painful to retrofit; everything downstream persists into
it from its first line.

Reference repo (read-only): `upstream prototype/`
(referred to below as REF).

## Step 1 — Evidence DB

**Goal**: the persistent contracts everything else produces/consumes.

- Flyway migration V1 in `evidence` implementing scope §4.4 sketch: `run`,
  `target`, `iteration`, `load_report`, `jfr_report`, `trajectory_event`.
- Java records (Jackson) for `LoadReport` (mirroring REF
  `benchmarks/k6-report.js`: `{repo, dateUtc, rps, totalRequests,
  latency{avg,p50,p95,p99,max}, failRate, checkPassRate,
  thresholds{verdict, breached[]}}`) and `ExperimentRecord` (hypothesis,
  prediction, evidenceBefore, change, evidenceAfter, delta, kept|reverted,
  **finding** — a one-sentence post-hoc mechanism note: what the evidence
  actually showed, e.g. the resource-cache falsification's "caches the
  path string, not the probe"; this is the payload future RAG memory and
  the regression table will want — modeled on REF
  `evidence/experiments/TEMPLATE-*.md`). These records are the JSONB
  payload contract: DB stores them verbatim.
- `EvidenceStore` (Spring Data JDBC): createRun, recordIteration, persistLoadReport /
  persistJfrReport (payload → JSONB, artifact → disk under
  `evidence/artifacts/<run-id>/...` + sha256), appendTrajectoryEvent (with
  tokens/cost), transitionRunStatus.
- `EvidenceStack` bootstrap: ensure the evidence compose project is up +
  healthy before a run; never tears it down per run.
- Run-ID `yyyyMMdd-HHmmss-<8char>` minted once per run (scope §10.9).

**Verify**: unit/integration test — boot Postgres (Testcontainers is fine
here, in the *test* envelope only), Flyway migrates, round-trip a LoadReport
+ JfrReport payload, artifact written with correct sha256, a trajectory row
lands with token/cost columns. Also parse REF's real
`evidence/advanced/h2/petclinic-degraded/load-report.json` into `LoadReport`.

## Step 3 — Target runner: build + docker lifecycle

**Goal**: Java service that builds the target and brings the stack up/down.

- `TargetBuilder`: `ProcessBuilder` of `cmd /c mvn -B -q -DskipTests
  package` in the target dir; capture `build.log`; 15-min timeout; pick the
  boot jar (largest jar under `target/`, excluding sources/javadoc/
  .original). Windows: Java 21+ refuses `.cmd`/`.bat` wrappers directly —
  go through `cmd /c`. `docker.exe`/`git.exe` spawn fine as-is.
- `TargetStack`: generate/reuse the REF `service/advanced/docker/` compose
  files (`Dockerfile.target`, `h2-target.yml`), drive `docker compose` via
  ProcessBuilder (build → `up -d --wait` → `stop`/`down -v`). Compose over
  Testcontainers — you need the k6 container + resource limits anyway.
- Every per-run compose invocation passes `-p <run-id>` (scope §10.16); the
  k6 service bind-mounts the evidence dir so `K6_SUMMARY_OUT` lands on the
  host. **The evidence Postgres project is never part of these files.**
- Resource budget baked in: service 2 CPU/2GB, JVM
  `-XX:ActiveProcessorCount=2 -Xms1536m -Xmx1536m`; healthcheck TCP 8080.

**Windows notes**: final system drives docker via Java ProcessBuilder — no
Git Bash, no path mangling. `DockerPaths.toMount(Path)`: absolute path,
backslashes → forward slashes (`C:/...`) for bind mounts (§10.10).
`MSYS_NO_PATHCONV=1` / `cygpath -w` only for manual Git Bash debugging.
Never JFR `disk=true` on Docker Desktop bind mounts.

**Verify**: from a JUnit/`main` run — build petclinic, bring the stack up,
health poll passes, `curl localhost:8080/owners/find` returns 200, teardown
is clean; the evidence Postgres stays up throughout.

## Step 6 — JFR aggregation + diff (pure Java, no LLM)

**Goal**: `captureAndAnalyzeJfr()` minus the LLM — aggregated report + diff.

- `Thresholds` config record: severity cutoffs ported from REF
  `jfr-diagnose.sh` (lock p95 ≤1/5/20ms, SocketRead p95 ≤1/5/20ms, GC p99
  ≤10/50/200ms, park p95 ≤1/10/50ms, counts 500/5000/20000/100).
- `JfrAnalyzer`: `RecordingFile.readAllEvents(path)`; per scope §4.3:
  - `jdk.ExecutionSample` → top-15 methods by sample count (first non-JDK
    frame = business frame) **plus top-3 raw frames per top stack** — the
    known bottleneck concentrates in JDK frames
    (`ClassLoader.loadClass`), which the business-frame rule truncates away.
  - `jdk.JavaMonitorEnter` → count, p50/p95/max of `duration`, top
    `monitorClass`.
  - `jdk.ThreadPark` → count, p95, top parks w/ business frame.
  - `jdk.SocketRead`/`SocketWrite` → count, p95.
  - `jdk.GCPhasePause` → count, p99.
  - `jdk.ObjectAllocationSample` → count, top `objectClass`.
  - `jdk.JavaErrorThrow`/`jdk.ExceptionThrow` → count, top classes.
- `JfrReport` JSON (~2–5 KB): per-signal {count, percentiles, severity,
  top-N}. **Diff**: given the run's previous `JfrReport`, emit per-signal
  count/percentile deltas (~0.5 KB). This — not raw events — is what the
  LLM sees.

**Verify** (the important gate): run the analyzer on REF's
`evidence/advanced/h3/spring-petclinic/profile.jfr` — it must independently
surface `JavaMonitorEnter` dominant (~72k events), lock contention CRITICAL,
matching REF's `jfr/diagnosis-report.md`. Then on REF's
`jar-unpack-exp/spring-petclinic/profile.jfr` — it must show the *shifted*
signature instead (`UrlJarFiles$Cache` absent; `JarFile`/`URLClassPath`
dominant, ~14k events). Two recordings, two opposite known signatures —
that pair is the aggregator's validation set. Add REF's
`resource-cache-exp/spring-petclinic/profile.jfr` as the third: same
shifted signals as jar-unpack within noise (`JarFile` 5,006 vs 7,622;
`URLClassPath` 9,159 vs 6,327) — the aggregator must read as "no change",
not improvement (the falsification reference). Also run it on your own
step-5 recording, and on a diff of the two REF recordings: the diff must
reproduce the monitor-class comparison tables of the jar-unpack experiment
report (that report's tables are the reference shape for the diff output).

## Step 7 — applyChange + revert + fix templates

**STATUS: gate green** (`Step7VerifyGate`, opt-in
`-Dstep7.gate=true`, ~20 s, 8 tests against a scratch clone — no
Docker/DB). Review-then-fix pass on the first hand-coded cut caught one
landmine worth recording: this machine's **system-level
`core.autocrlf=true`**. A default clone checks out CRLF; setting
`core.autocrlf=false` *after* checkout leaves ~68 files
phantom-modified — invisible at clone time (the clone's status is clean
while its config still says true) — and the first `git add -A` commits
the entire tree as line-ending noise. Fix: pin at clone time
(`git clone -c core.autocrlf=false`, §10.33 extended). Step 10's
`SeededTarget` clones must do the same. Also fixed en route: hikari
template path typo (`resource`→`resources`), `*` instead of `=`
separator, a `found` flag never set (duplicate property on replace);
registry reports unknown ids as unknown *before* the §10.35 admission
check (hallucination ≠ policy); no-op applies (byte-identical content)
reject parseably instead of surfacing git's raw "nothing to commit"
exit; `git`/`gitOutput` widened to public so gates can drive git;
validatePath uses toRealPath for symlink escapes (§10.2), not just
lexical normalize; dead duplicate `ApplyResult` removed.

**Goal**: safe, machine-checkable mutations of the target tree.

- `ChangeApplier`: apply edits as **full-file replacement** —
  `[{path, content}]`, per-file cap ~400 lines (§10.3; no diffs) — then
  `git add -A && git commit -m "<description>"`. Missing path creates the
  file; existing files replaced whole; no deletions (§10.12).
- `revertTo(commit)` = `git reset --hard <sha>` + `git clean -fd`; assert
  `git status --porcelain` empty, else fall back to `git clean -fdx`
  (§10.13).
- **Fix templates** (§10.23 + admission rule §10.35): the library admits
  only measured templates. Now: `jar-unpack` (validated — REF
  `jar-unpack-exp` `Dockerfile.target-unpacked`). `hikari-pool-size` and
  `jvm-opts` enter at step 10 when per-seed validation measures them.
  Candidates NOT in the library until hand-validated:
  `disable-resource-url-filter` (small config-code change — the
  likely-correct S1 iteration-3 fix), `resource-url-cache-warmup`,
  `classpath-launch`. `spring-resources-cache` is FALSIFIED (REF
  `resource-cache-exp`) and never enters. Template = id + params,
  validated server-side; expansion writes normal committed edits into the
  target tree — same gates as manual edits, no bypass.
- Track `baselineSha` at loop start; every kept change advances it.
- **Change transparency** (scope §10.28): record files touched + line counts
  on the iteration row — the anti-gaming audit trail eval flags against the
  expected edit surface.
- **Code-touch gate** (scope §10.31): edits touching `.java` trigger the
  target's own test suite after compile, before smoke; config-only edits
  skip it (speed).
- **Diff base rule** (scope §10.32): JFR diffs compare against the current
  kept state's most recent benchmark recording — never a reverted
  iteration's.

**Verify**: unit test — apply a change, commit, revert, assert contents and
`git log` match; template expansion of `hikari-pool-size` produces a valid
committed diff and reverts cleanly.

## Step 9 — The agent loop

**Goal**: close the loop per scope §4.2 — with ledger, guardrails, resume.

- `AgentLoop`: baseline ×3 (or cache hit, §10.24) → iterate ≤5: JFR+diff →
  LLM decide (schema-validated) → ledger update → apply → rebuild+smoke →
  benchmark → keep/revert → `Iteration` row in Postgres + trajectory event
  per LLM/tool call (tokens + $).
- System prompt: role (JVM performance diagnostician), tool docs, hypothesis
  menu (H1 external I/O, H2 blocking/park, H3 GC, H4 CPU, H5 lock
  contention, H6 allocation, H7 exceptions — from REF jfr-diagnose.sh), and
  the rules: one change per iteration, must runBenchmark after every
  change, hypothesis before action, ledger updated every iteration,
  **investigate before proposing** — readSource into the suspect call path
  before the first applyChange (the resource-cache falsification is the
  cautionary tale: a plausible-sounding property that never touched the
  mechanism; 10 minutes of source reading beats a 30-minute benchmark on
  a guess).
- Keep decision (§10.5 keep-rule v2, rev 5): classic — RPS **or** p95
  improves beyond its own noise floor (failRate not worse) — OR
  verified-mechanism keep: prediction confirmed (named signal dropped
  >50%, a latency/throughput metric improved) with bounded p95 regression
  (≤50% default). Record `keep_type` (`RPS`|`P95`|`MECHANISM`) per keep.
  Rationale: under fixed 200 VUs, RPS ⇔ mean latency (Little's Law) and
  RPS is the cleaner signal; p95 remains the diagnostic that catches
  bottleneck *shifts* (the S1 saddle was invisible to RPS-only).
  Termination: per-target target vector (scope §6) or iteration cap —
  never the global 500ms threshold (not physically reachable on this
  envelope).
- Guardrails (§10.25): env caps $ / wall-clock / tokens / iterations;
  exceeded → run ABORTED, partial evidence retained — **and any
  applied-but-unbenchmarked change is reverted to the last kept sha** (no
  change survives unbenchmarked, aborts included).
- **Provider-call timeout** (lesson from step 8, D7): set an explicit HTTP
  timeout (env `DIAG_LLM_TIMEOUT_MS`, default 120000; in Spring AI 2.0.1 Anthropic
  uses OkHttp via `AnthropicHttpClientBuilderCustomizer`) — a hung LLM call burns
  the wall-clock guardrail *silently* (no tokens spent, no response, clock
  running) and the wall-clock cap only catches it after the damage. A timeout counts
  as a failed LLM turn entering the bounded backoff retry path (D3). Motivation is
  local and measured: the dev Claude Code config here runs `API_TIMEOUT_MS=3000000`
  (~50 min) precisely because provider hangs happen — the loop must fail fast instead.
- **Single-flight + startup janitor** (§10.27): a second run refuses to
  start while a RUNNING row exists; on startup, tear down orphaned run-id
  compose projects and verify no stray containers are eating the VM budget.
- **Per-iteration tool-call bound** (≤10, §10.34): a model that only wants
  to `readSource` endlessly gets cut off, not paid for.
- Resume (§10.19): reload RUNNING run → verify target `HEAD == last kept
  tree_sha` (else `revertTo`) → continue at next iteration.

**Verify**: dry-run with a scripted fake LLM (canned valid + canned invalid
decisions) — loop mechanics, keep/revert, ledger rows, guardrail abort, kill
-and-resume, and evidence records all work before real model calls cost
money. Then one real S1 run end-to-end.
