# v1.0 Build Steps

Companion to `v1.0-scope.md`. Each step has a **goal**, **what to build**,
**key APIs/pointers**, and a **verify** gate — do not move on until the gate
passes. Order is deliberate: no LLM until step 8, so every piece is
deterministically testable first. Postgres comes first (step 1) because it
is cheap for us and painful to retrofit; everything downstream persists into
it from its first line.

Reference repo (read-only): `C:/study/java-backend-quality-analyzer/`
(referred to below as REF).

---

## Step 0 — Repo & target setup

**Goal**: buildable skeleton + a working copy of the target app + the
evidence envelope.

- Create Maven multi-module project: parent pom + `evidence`, `target-runner`,
  `agent-core`, `eval`. Java 21, Spring Boot 4.1.1, Spring AI (add BOM now,
  use later). `evidence` gets `spring-boot-starter-data-jpa` +
  `flyway-core` + `postgresql` + `jackson` now (scope §10.1 note).
- Environment check: Docker Desktop on the **WSL2 backend** (`docker info`).
  Docker VM headroom: stack budget 2 CPU/2GB + k6 1 CPU/512MB + evidence
  Postgres 0.5 CPU/512MB + overhead → ≥4 CPUs / 6GB allocated.
- Clone stock spring-petclinic into `targets/petclinic` (gitignored — same
  convention as REF). The clone has git history — no `git init`. Add the
  target-runtime packaging files (`Dockerfile.target`, compose overrides,
  scope §10.7), **make a baseline commit**, record its sha as `baselineSha`
  (this is what `revertTo()` resets to; uncommitted packaging dies to
  `git clean -fd`).
- `git -C targets/petclinic config core.autocrlf false` — Windows autocrlf
  shows phantom modifications on agent-written files and breaks the
  revert-assertion (scope §10.33).
- Local paths: `targets/`, `evidence/artifacts/`, `benchmarks/`,
  `docker/evidence/` at repo root.
- `docker/evidence/docker-compose.yml`: Postgres (pin a major version),
  project name `diag-evidence`, named volume, resource caps 0.5 CPU / 512MB,
  port 5432, credentials via env. **Own project, always-on — never included
  in a per-run compose invocation** (scope §5, §10.16).
- Repo hygiene: `.gitignore` (`targets/`, `*.jfr`, `evidence/artifacts/`,
  `.idea/`, `docker/evidence/*.env`); root `README.md` (two paragraphs +
  pointer to `docs/`). `AGENTS.md` later.

**Verify**: `mvn -q package` green; `mvn -f targets/petclinic package
-DskipTests` produces a boot jar; `git -C targets/petclinic rev-parse HEAD`
returns the baseline commit; `docker info` shows WSL2; `docker compose -f
docker/evidence/docker-compose.yml -p diag-evidence up -d` then `psql`/any
client connects.

## Step 1 — Evidence DB

**Goal**: the persistent contracts everything else produces/consumes.

- Flyway migration V1 in `evidence` implementing scope §4.4 sketch: `run`,
  `target`, `iteration`, `load_report`, `jfr_report`, `trajectory_event`.
- Java records (Jackson) for `LoadReport` (mirroring REF
  `benchmarks/k6-report.js`: `{repo, dateUtc, rps, totalRequests,
  latency{avg,p50,p95,p99,max}, failRate, checkPassRate,
  thresholds{verdict, breached[]}}`) and `ExperimentRecord` (hypothesis,
  prediction, evidenceBefore, change, evidenceAfter, delta, kept|reverted,
  **finding** — a one-sentence post-hoc mechanism note: what the evidence
  actually showed, e.g. the resource-cache falsification's "caches the
  path string, not the probe"; this is the payload future RAG memory and
  the regression table will want — modeled on REF
  `evidence/experiments/TEMPLATE-*.md`). These records are the JSONB
  payload contract: DB stores them verbatim.
- `EvidenceStore` (JPA): createRun, recordIteration, persistLoadReport /
  persistJfrReport (payload → JSONB, artifact → disk under
  `evidence/artifacts/<run-id>/...` + sha256), appendTrajectoryEvent (with
  tokens/cost), transitionRunStatus.
- `EvidenceStack` bootstrap: ensure the evidence compose project is up +
  healthy before a run; never tears it down per run.
- Run-ID `yyyyMMdd-HHmmss-<8char>` minted once per run (scope §10.9).

**Verify**: unit/integration test — boot Postgres (Testcontainers is fine
here, in the *test* envelope only), Flyway migrates, round-trip a LoadReport
+ JfrReport payload, artifact written with correct sha256, a trajectory row
lands with token/cost columns. Also parse REF's real
`evidence/advanced/h2/petclinic-degraded/load-report.json` into `LoadReport`.

## Step 2 — k6 script for petclinic (artifact, not code)

**Goal**: a committed load-test.js you never regenerate at runtime.

- Port REF `service/advanced/k6/template-form.js` by hand for petclinic:
  setup seeds 50 owners via `POST /owners/new` (id from redirect
  `Location`), default(): 90% `GET /owners/{id}`, 10% `POST /owners/new`.
- Profile as constants: `vus=200, duration=60s, ramp=10s (+5s down)`.
- Thresholds: `p(95)<500`, `http_req_failed rate<0.01`, `checks rate>0.95`.
- `handleSummary` writes the k6 summary JSON to `K6_SUMMARY_OUT` (env).
- **Read-back check** (anti-gaming, scope §10.28): after each
  `POST /owners/new`, immediately `GET` the new id and assert the name
  substring — writes must actually land, or the run fails the gate.
- Commit to `benchmarks/petclinic/load-test.js`. Artifact is the contract —
  its sha feeds the baseline-cache key (§10.24).

**Verify**: eyeball against REF's generated
`evidence/advanced/h2/petclinic-degraded/load-test.js` — same shape/slots.

## Step 3 — Target runner: build + docker lifecycle

**Goal**: Java service that builds the target and brings the stack up/down.

- `TargetBuilder`: `ProcessBuilder` of `cmd /c mvn -B -q -DskipTests
  package` in the target dir; capture `build.log`; 15-min timeout; pick the
  boot jar (largest jar under `target/`, excluding sources/javadoc/
  .original). Windows: Java 21+ refuses `.cmd`/`.bat` wrappers directly —
  go through `cmd /c`. `docker.exe`/`git.exe` spawn fine as-is.
- `TargetStack`: generate/reuse the REF `service/advanced/docker/` compose
  files (`Dockerfile.target`, `h2-target.yml`), drive `docker compose` via
  ProcessBuilder (build → `up -d --wait` → `stop`/`down -v`). Compose over
  Testcontainers — you need the k6 container + resource limits anyway.
- Every per-run compose invocation passes `-p <run-id>` (scope §10.16); the
  k6 service bind-mounts the evidence dir so `K6_SUMMARY_OUT` lands on the
  host. **The evidence Postgres project is never part of these files.**
- Resource budget baked in: service 2 CPU/2GB, JVM
  `-XX:ActiveProcessorCount=2 -Xms1536m -Xmx1536m`; healthcheck TCP 8080.

**Windows notes**: final system drives docker via Java ProcessBuilder — no
Git Bash, no path mangling. `DockerPaths.toMount(Path)`: absolute path,
backslashes → forward slashes (`C:/...`) for bind mounts (§10.10).
`MSYS_NO_PATHCONV=1` / `cygpath -w` only for manual Git Bash debugging.
Never JFR `disk=true` on Docker Desktop bind mounts.

**Verify**: from a JUnit/`main` run — build petclinic, bring the stack up,
health poll passes, `curl localhost:8080/owners/find` returns 200, teardown
is clean; the evidence Postgres stays up throughout.

## Step 4 — Target runner: k6 execution + report

**Goal**: `runBenchmark()` works with zero AI involved, persisted to DB.

- `BenchmarkRunner`: smoke gate first (env override `K6_VUS=2 K6_DURATION=5s
  K6_RAMP=1s K6_ENTITY_COUNT=3`); require `http_reqs.count>0 &&
  checks.rate>0`, else a NOT_TESTABLE `LoadReport` (finding, not exception).
  Smoke writes summary + JFR into its own `smoke-<n>` subdir — never
  harvestable as a benchmark recording (§10.15).
- Full run with the committed profile. k6 exit 99 = measured FAIL — parse
  the report anyway.
- **Post-run envelope assertion** (scope §10.28): `docker inspect` the
  target container, assert NanoCpus/Memory == budget. A run against a
  tampered envelope is invalid, not FAIL.
- k6 summary JSON → `LoadReport` → `EvidenceStore.persistLoadReport` with
  label (`baseline-1..3` / `iter-<n>` / `smoke-<n>`).

**Verify**: run against petclinic → reproduce the *stock* baseline ballpark
(REF h3): rps ~189, p95 ~2500ms, verdict FAIL with `p(95)<500` breached,
row visible in Postgres, artifact + sha256 on disk. Wildly off → fix the
envelope (CPU/memory limits) before proceeding.

## Step 4b — Manual fix-validation gate (no code)

**Goal**: measure the unpack fix's real effect before any LLM depends on it.

**STATUS (2026-09-03): executed out-of-band, pre-repo** — in REF at
`evidence/advanced/jar-unpack-exp/spring-petclinic/experiment-report.md`,
against the h3 packed baseline. Result: RPS +47%, p50 −87%, lock rate −81%
(`UrlJarFiles$Cache` 71,193 → 0) — but **p95 +24%, p99 +66%, max +139%**.
Neither dud nor clean win: a **saddle**. Consequences already folded into
scope rev 3 — keep-rule v2 (verified-mechanism keeps, §10.5), prediction
field in the decision schema (§10.21), S1 ground truth as a two-step
sequence (§3). When the repo exists: import `Dockerfile.target-unpacked`
as the `jar-unpack` template's reference implementation and log the report
as a `fix-validation` run. **Remaining hand-calibration (~30 min,
recommended):** unpack + `spring.web.resources.cache.period` (the report's
"Next Experiments" #1) — settles S1's true convergence depth
(open-questions A1b).

- Edit `targets/petclinic/Dockerfile.target` to run from extracted classes:
  first stage runs the fat jar with `-Djarmode=tools` (Boot 3.3+; older 3.x:
  `-Djarmode=layertools`) to `extract`, runtime stage `java -jar`s the
  unpacked app — never the fat jar.
- Run the full pipeline once (build → up → smoke → k6 @ 200 VUs → JFR);
  record as a `fix-validation` run in the DB + an experiment record.
- Decide by the measured p95 (calibrates scope §6 tiers): big drop (≥2x,
  ≤~1200ms) → real; improves but >500ms → PASS tier is the honest target;
  no movement → wrong fix, diagnose by hand now while it's cheap, update
  scope §3.
- Afterwards: reset the target tree to `baselineSha` (agent starts
  unfixed); archive the validated Dockerfile under `benchmarks/` — it is
  also the reference implementation of the `jar-unpack` fix template
  (step 7).

**Verify**: post-fix load-report + experiment record in the DB; target tree
back at `baselineSha` (`git status` clean).

## Step 5 — JFR capture (always on)

**Goal**: every benchmark run produces a `profile.jfr`, from Java.

- JFR opts are part of the single stack mode (§10.6): the target container
  always boots with
  `-XX:StartFlightRecording=name=run,settings=profile,dumponexit=true,filename=/jfr-repo/<per-run-subdir>/profile.jfr`
  with the evidence dir bind-mounted at `/jfr-repo`. Create the subdir on
  the host *before* `up` — missing dir = JFR silently doesn't start.
- Sequence: up → benchmark load → graceful `compose stop` (15s grace for
  dumponexit) → file on host → `EvidenceStore.persistJfrReport` (artifact
  path + sha256; payload filled by step 6).

**Verify**: `jfr summary` (JDK CLI) on the file shows ~60s of
profile-settings events incl. `jdk.ExecutionSample`, `jdk.JavaMonitorEnter`;
artifact + hash recorded in Postgres.

## Step 6 — JFR aggregation + diff (pure Java, no LLM)

**Goal**: `captureAndAnalyzeJfr()` minus the LLM — aggregated report + diff.

- `Thresholds` config record: severity cutoffs ported from REF
  `jfr-diagnose.sh` (lock p95 ≤1/5/20ms, SocketRead p95 ≤1/5/20ms, GC p99
  ≤10/50/200ms, park p95 ≤1/10/50ms, counts 500/5000/20000/100).
- `JfrAnalyzer`: `RecordingFile.readAllEvents(path)`; per scope §4.3:
  - `jdk.ExecutionSample` → top-15 methods by sample count (first non-JDK
    frame = business frame) **plus top-3 raw frames per top stack** — the
    known bottleneck concentrates in JDK frames
    (`ClassLoader.loadClass`), which the business-frame rule truncates away.
  - `jdk.JavaMonitorEnter` → count, p50/p95/max of `duration`, top
    `monitorClass`.
  - `jdk.ThreadPark` → count, p95, top parks w/ business frame.
  - `jdk.SocketRead`/`SocketWrite` → count, p95.
  - `jdk.GCPhasePause` → count, p99.
  - `jdk.ObjectAllocationSample` → count, top `objectClass`.
  - `jdk.JavaErrorThrow`/`jdk.ExceptionThrow` → count, top classes.
- `JfrReport` JSON (~2–5 KB): per-signal {count, percentiles, severity,
  top-N}. **Diff**: given the run's previous `JfrReport`, emit per-signal
  count/percentile deltas (~0.5 KB). This — not raw events — is what the
  LLM sees.

**Verify** (the important gate): run the analyzer on REF's
`evidence/advanced/h3/spring-petclinic/profile.jfr` — it must independently
surface `JavaMonitorEnter` dominant (~72k events), lock contention CRITICAL,
matching REF's `jfr/diagnosis-report.md`. Then on REF's
`jar-unpack-exp/spring-petclinic/profile.jfr` — it must show the *shifted*
signature instead (`UrlJarFiles$Cache` absent; `JarFile`/`URLClassPath`
dominant, ~14k events). Two recordings, two opposite known signatures —
that pair is the aggregator's validation set. Add REF's
`resource-cache-exp/spring-petclinic/profile.jfr` as the third: same
shifted signals as jar-unpack within noise (`JarFile` 5,006 vs 7,622;
`URLClassPath` 9,159 vs 6,327) — the aggregator must read as "no change",
not improvement (the falsification reference). Also run it on your own
step-5 recording, and on a diff of the two REF recordings: the diff must
reproduce the monitor-class comparison tables of the jar-unpack experiment
report (that report's tables are the reference shape for the diff output).

## Step 7 — applyChange + revert + fix templates

**Goal**: safe, machine-checkable mutations of the target tree.

- `ChangeApplier`: apply edits as **full-file replacement** —
  `[{path, content}]`, per-file cap ~400 lines (§10.3; no diffs) — then
  `git add -A && git commit -m "<description>"`. Missing path creates the
  file; existing files replaced whole; no deletions (§10.12).
- `revertTo(commit)` = `git reset --hard <sha>` + `git clean -fd`; assert
  `git status --porcelain` empty, else fall back to `git clean -fdx`
  (§10.13).
- **Fix templates** (§10.23 + admission rule §10.35): the library admits
  only measured templates. Now: `jar-unpack` (validated — REF
  `jar-unpack-exp` `Dockerfile.target-unpacked`). `hikari-pool-size` and
  `jvm-opts` enter at step 10 when per-seed validation measures them.
  Candidates NOT in the library until hand-validated:
  `disable-resource-url-filter` (small config-code change — the
  likely-correct S1 iteration-3 fix), `resource-url-cache-warmup`,
  `classpath-launch`. `spring-resources-cache` is FALSIFIED (REF
  `resource-cache-exp`) and never enters. Template = id + params,
  validated server-side; expansion writes normal committed edits into the
  target tree — same gates as manual edits, no bypass.
- Track `baselineSha` at loop start; every kept change advances it.
- **Change transparency** (scope §10.28): record files touched + line counts
  on the iteration row — the anti-gaming audit trail eval flags against the
  expected edit surface.
- **Code-touch gate** (scope §10.31): edits touching `.java` trigger the
  target's own test suite after compile, before smoke; config-only edits
  skip it (speed).
- **Diff base rule** (scope §10.32): JFR diffs compare against the current
  kept state's most recent benchmark recording — never a reverted
  iteration's.

**Verify**: unit test — apply a change, commit, revert, assert contents and
`git log` match; template expansion of `hikari-pool-size` produces a valid
committed diff and reverts cleanly.

## Step 8 — Spring AI tool wiring + structured decisions

**Goal**: the 4 tools callable by the model; decisions validated before use.

- Pin Spring AI 1.0.x GA, `@Tool` idiom on `ChatClient` (§10.8). Provider =
  whichever API key you have; tool-calling reliability is the criterion;
  provider/model + **generation params (temperature, max tokens)** recorded
  on the run row as `gen_params` (attribution, §10.20/§10.34).
- Register the 4 tools (scope §4.1): `runBenchmark`, `captureAndAnalyzeJfr`
  (report + diff), `readSource`, `applyChange` (edits or fixTemplate).
  Compact JSON returns — the model reads them verbatim.
- **Structured decision schema** (§10.21), validated (Jackson + bean
  validation) before any apply:

```json
{ "hypothesis": {"category": "H5", "confidence": 0.8, "rationale": "..."},
  "ledger": {"category": "H5", "direction": "strengthen", "reason": "..."},
  "change": {"kind": "template", "template": "jar-unpack"}
          | {"kind": "edits", "edits": [{"path": "...", "content": "..."}]} }
```

  Invalid → error envelope back to the model, one retry, then WASTED
  iteration (taxonomy row 1).

**Verify**: a manual chat turn where the model calls `runBenchmark` and
returns real numbers; a hand-fed malformed decision is rejected with a
parseable error and nothing applied.

## Step 9 — The agent loop

**Goal**: close the loop per scope §4.2 — with ledger, guardrails, resume.

- `AgentLoop`: baseline ×3 (or cache hit, §10.24) → iterate ≤5: JFR+diff →
  LLM decide (schema-validated) → ledger update → apply → rebuild+smoke →
  benchmark → keep/revert → `Iteration` row in Postgres + trajectory event
  per LLM/tool call (tokens + $).
- System prompt: role (JVM performance diagnostician), tool docs, hypothesis
  menu (H1 external I/O, H2 blocking/park, H3 GC, H4 CPU, H5 lock
  contention, H6 allocation, H7 exceptions — from REF jfr-diagnose.sh), and
  the rules: one change per iteration, must runBenchmark after every
  change, hypothesis before action, ledger updated every iteration,
  **investigate before proposing** — readSource into the suspect call path
  before the first applyChange (the resource-cache falsification is the
  cautionary tale: a plausible-sounding property that never touched the
  mechanism; 10 minutes of source reading beats a 30-minute benchmark on
  a guess).
- Keep decision (§10.5 keep-rule v2, rev 5): classic — RPS **or** p95
  improves beyond its own noise floor (failRate not worse) — OR
  verified-mechanism keep: prediction confirmed (named signal dropped
  >50%, a latency/throughput metric improved) with bounded p95 regression
  (≤50% default). Record `keep_type` (`RPS`|`P95`|`MECHANISM`) per keep.
  Rationale: under fixed 200 VUs, RPS ⇔ mean latency (Little's Law) and
  RPS is the cleaner signal; p95 remains the diagnostic that catches
  bottleneck *shifts* (the S1 saddle was invisible to RPS-only).
  Termination: per-target target vector (scope §6) or iteration cap —
  never the global 500ms threshold (not physically reachable on this
  envelope).
- Guardrails (§10.25): env caps $ / wall-clock / tokens / iterations;
  exceeded → run ABORTED, partial evidence retained — **and any
  applied-but-unbenchmarked change is reverted to the last kept sha** (no
  change survives unbenchmarked, aborts included).
- **Single-flight + startup janitor** (§10.27): a second run refuses to
  start while a RUNNING row exists; on startup, tear down orphaned run-id
  compose projects and verify no stray containers are eating the VM budget.
- **Per-iteration tool-call bound** (≤10, §10.34): a model that only wants
  to `readSource` endlessly gets cut off, not paid for.
- Resume (§10.19): reload RUNNING run → verify target `HEAD == last kept
  tree_sha` (else `revertTo`) → continue at next iteration.

**Verify**: dry-run with a scripted fake LLM (canned valid + canned invalid
decisions) — loop mechanics, keep/revert, ledger rows, guardrail abort, kill
-and-resume, and evidence records all work before real model calls cost
money. Then one real S1 run end-to-end.

## Step 10 — Target registry + seeds S2–S4

**Goal**: the matrix from scope §3, deterministically reproducible.

- `TargetRegistry`: target = {id, base clone, seed patch, baselineSha,
  k6 script, ground_truth_category, ground_truth_fix, profile_hash}.
- `SeededTarget`: apply committed patch to pristine base → commit → record
  sha + ground truth. Reset = the same `revertTo()`.
- Seeds: S2 `hikari maximumPoolSize=2` (application.properties), S3 JVM
  `-Xmx256m` override in `Dockerfile.target`, S4 REF practice-mvc port
  (synchronized hotspot). Each gets its baseline ×3 + noise floor measured
  once (cached per §10.24).
- Sanity-check each seed's ground truth by hand once: one JFR aggregation on
  the seeded app must show the expected dominant signal (S2 → pool-wait
  parks/monitors, S3 → GC CRITICAL, S4 → app-class monitor contention) —
  fix the seed if it doesn't produce its intended bottleneck.
- **Per-seed fix-validation** (scope §3, §10.29 — the 4b gate, once per
  seed): apply the seed's expected fix by hand, one benchmark, record it as
  a `fix-validation` run, revert to the seed's `baselineSha`. Calibrates the
  effectiveness metric and proves the fix templates are sufficient — before
  the matrix ever runs.

**Verify**: registry lists 4 targets; seeding + reset round-trips cleanly;
per-target baseline rows in the DB; each seed's JFR shows its intended
dominant signal.

## Step 11 — Eval harness + reports

**Goal**: every run scored; results comparable across runs.

- Scoring (scope §6.2), computed from the DB only:
  - **accuracy**: final-kept iteration's hypothesis category (no kept
    change → last iteration's) vs. `ground_truth_category`.
  - **effectiveness**: p95 delta vs. baseline beyond noise floor;
    converged y/n.
  - **efficiency**: iterations used, tokens, $.
- Headline accuracy comes from **≥2 matrix repeats** (scope §6); per-target
  detail is the unit of record. Attribution groups include `gen_params`
  (§10.34).
- Regression table: runs grouped by (prompt_hash, model,
  aggregator_version) × target — the "did my prompt change help" view
  (§10.20).
- HTML report (§10.26): self-contained generated file per run (timeline,
  per-iteration hypothesis/change/outcome, before/after p95 bars,
  trajectory table with tokens/$, links to artifacts) + matrix summary
  table.

**Verify**: after one S1 run — score row correct against ground truth;
re-running with a trivial prompt tweak produces a second regression-table
group; HTML report opens standalone with no missing artifacts.

## Step 12 — Full matrix run against the success criterion

**Goal**: v1.0 done.

- Run the matrix (S1–S4) through the loop, guardrails on, baselines cached.
- Judge against scope §6: PASS = matrix autonomy + accuracy ≥70% + ≥2 of 4
  converged + reports with no manual collation + guardrails/resume proven.
  STRETCH = ≥85% accuracy and S5 in.
- If it fails, debug in this order: JfrReport quality → prompt → tool
  results → model. Change one thing, re-run, and let the regression table
  record what happened (eat your own evidence format).
